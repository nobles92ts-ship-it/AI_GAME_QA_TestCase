# S3 문장화 동시성 실측 (2026-08-16)

**결론: 300 TC 기준 순차 40분 46초 → 동시 3이면 16분 36초. 절감 24분(59%).**
품질 저하 없음(10/10 검증 통과·재시도 0). 동시 3 채택 권고.

## 왜 쟀나

`run_pipeline_full.sh` 160행 `while [[ $CI -lt $N_CHUNK ]]` 루프가 문장화 청크를 하나씩 돈다.
같은 파일의 S4 렌즈(3종)와 커버리지 원장(`TCTEAM_COV_PAR`, 기본 3)은 이미 병렬인데 **문장화만 동시 1**이다.
자동_사냥_기능_v3 실런에서 문장화가 33분 58초로 전 구간 중 최대 단일 비용이었다.

## 방법

파이프라인의 **호출 경로를 그대로 복제**했다 — `pipeline_retry.sh` → `run-agent.sh` → `claude -p --model sonnet`,
프롬프트는 `extract-s3-rules` 산출(2,617자) + S3 청크 템플릿 원문, 검증은 `chain_helpers.js validate-chunk`.

- 하네스: `scratchpad/s3_bench.sh` · 작업 폴더는 스크래치(실 spec 무접촉)
- **캐시 오염 방지**: 실험군마다 서로 다른 청크를 썼다. 같은 청크를 재실행하면 프롬프트 캐시 히트로 병렬이 부당하게 빨라 보인다.
- 골격: 자동_사냥_기능_v3 `tc_skeleton.json` 238행 = 10청크(25행 단위, 마지막 13행)
- 측정 시각 2026-08-16 12:22~12:34, 같은 머신·같은 1시간 내

### 관측 1 — 동시 실행이 청크 지연을 거의 늘리지 않는다

K=3에서 평균 지연이 오히려 **-13.9%**(표본 변동), K=4에서 **+13.2%**.
동시 4까지는 호출당 지연이 사실상 그대로다 = **웨이브 수만큼 그대로 줄어든다.**

### 관측 2 — 지연은 행 수가 아니라 분산이 지배한다

가장 **작은** 청크(225~237, 13행)가 **213초로 가장 오래** 걸렸다. 25행 청크는 96~185초.
행 수로 지연을 예측할 수 없다 → 청크 크기를 줄여 균등화하는 접근은 효과가 없다.

### 관측 3 — 웨이브 벽시계는 평균이 아니라 최댓값이 정한다

B의 벽시계 126초 = max(96,124,126). C의 213초 = max(118,132,144,213).
따라서 K를 키울수록 `max-of-K`가 커져 **이득이 체감**한다. 아래 환산은 이 효과를 부트스트랩으로 반영했다.

## 구현 시 반드시 지킬 것

1. **`RUN_LLM_ERRLOG`를 호출별로 분리한다.** `run_pipeline_full.sh` 85행 주석의 경고 그대로 —
   공유하면 재시도 분류기가 **다른 호출의 stderr를 읽어** 오분류한다. 하네스도 `.err_<S>.log`로 분리해 통과했다.
2. **S4 렌즈 블록(275~290행) 패턴을 그대로 쓴다** — `( ... ) &` + PID 수집 + `wait` per PID + rc 분기.

3. **청크 재시도는 웨이브 안에서 독립 유지** — 현행 2회 실패 시 `fail`. 병렬에서도 청크별로 지역화할 것.
4. 검증은 지금처럼 청크별 `validate-chunk`. 병렬로 인한 품질 저하는 관측되지 않았다(10/10 통과, 재시도 0).

## 판정 — 채택 (2026-08-19, 형근님 승인)

**기본값 K=4로 배선 완료.** 위 권고(3)보다 한 단계 높다.

### 왜 3이 아니라 4인가

권고 3의 근거는 "K=4에서 지연 +13.2%"였는데, 그 증가분이 실험 C의 **213초 청크 하나**에서 나온다.
그 청크는 마지막 13행짜리이고, **같은 문서의 관측 2가 바로 그 청크를 "행 수로 설명되지 않는 분산
이상치"로 지목**한다. 이상치라고 부른 값으로 K=4를 깎은 셈이다. 그 하나를 제외하면 실험 C 평균은
**131.3초로 K=1 기준선(135.5초)보다 낮다** — K=4에서 지연이 팽창한다는 증거가 남지 않는다.

n=4 표본이라 확정은 아니다. 그래서 **K=6 이상은 올리지 않았다**(실측 표본 없음). 다음 실런에서
청크별 지연을 보고, 이상 없으면 6 → 8 순으로 표본을 만들며 올린다.

### 배선 내용 (`run_pipeline_full.sh` 155~229행)

- `TCTEAM_S3_PAR` (기본 4) — 웨이브 배치. S4 커버리지 원장(`TCTEAM_COV_PAR`)과 동일 형태.
- 구현 조건 4개 전부 반영: ERRLOG 청크별 분리 · S4 렌즈 패턴(`( ) &` + PID + `wait` + rc 분기) ·
  재시도 서브셸 지역화 · `validate-chunk` 청크별 유지.
- **문서에 없던 조건 1개 추가**: `.chunk_verr.txt`(검증 실패 사유)도 **청크별 분리**해야 한다
  (`.chunk_verr_<S>.txt`). 공유하면 재시도 프롬프트에 **남의 실패 사유**가 붙는다 — ERRLOG와 같은
  종류의 함정인데 구현 조건 1에는 빠져 있었다.
- **fail-fast 보존**: 청크가 검증 2회 실패하면 남은 웨이브를 띄우지 않는다. S4 렌즈·커버리지는
  끝까지 돌지만(산출물이 `--start-from s4` 재개에 쓰임), S3는 재진입 시 `fmap_chunk_*.json`을 전부
  지우고 다시 만들어 **계속 띄운 청크의 산출물이 재개에 쓰이지 않는다 = 순수 낭비**.
  초판 배선은 이걸 놓쳤고 하네스 T5가 잡았다.
