### 1단계: TC 읽기 + 품질 리뷰

#### 🛡️ 하드 가드 (필수 — 가이드 위반 시 self-fail)

진입 즉시 아래 검증을 수행한다. **위반 시 즉시 status=fail 반환**:

```bash
# ① 핸드오프에서 SNAPSHOT 경로 추출
SNAPSHOT="<핸드오프의 '시트 스냅샷' 또는 'tc_after_fix1.json' 경로>"

# ② 파일 존재 검증
if [ ! -f "$SNAPSHOT" ]; then
  echo '{"status":"fail","error":"snapshot_not_found","snapshot":"'"$SNAPSHOT"'"}' > "$SPECS/[기능명]/step_result.json"
  exit 1
fi

# ③ 스냅샷 무결성 검증 (행 수 ≥ 1)
#    공용 로더 사용 — `✔ 인증` 프리픽스 strip + rows/values 겸용 (단위 테스트: tests/run_tests.js)
#    (회귀 주의 2026-06-10 F4-A1: 과거 require()+r.values 직파싱은 정상 스냅샷을 0행으로 오판해 무조건 snapshot_empty fail)
ROW_COUNT=$("$NODE" "{WORK_ROOT}/scripts/util/load_snapshot.js" "$SNAPSHOT" --count 2>/dev/null || echo 0)
if [ "$ROW_COUNT" -lt 1 ]; then
  echo '{"status":"fail","error":"snapshot_empty"}' > "$SPECS/[기능명]/step_result.json"
  exit 1
fi

# ④ progress.log에 가드 통과 기록
echo "[$(date '+%Y-%m-%d %H:%M:%S')] STEP 6 | guard | snapshot=$SNAPSHOT rows=$ROW_COUNT — Sheets API BLOCKED" >> "$SPECS/[기능명]/progress.log"
```

**🚫 절대 금지**:
- `read_gsheet_data.js` 호출 (스냅샷 무결성 통과 시)
- Sheets API `spreadsheets.values.get` / `spreadsheets.values.batchGet` 호출
- Google Sheets MCP 도구 (`mcp__google-sheets__get_sheet_data` 등) 호출

위반 자동 감지 (자체 점검 — 수정 코드 실행 직전):
```bash
if grep -E "(read_gsheet_data\.js|spreadsheets\.values\.(get|batchGet)|google-sheets__get_sheet_data)" "$SPECS/[기능명]/progress.log" 2>/dev/null | tail -1 | grep -v "guard"; then
  echo "[GUARD-VIOLATION] STEP 6 — Sheets API 호출 감지" >&2
  echo '{"status":"fail","error":"sheets_api_violation_in_step6"}' > "$SPECS/[기능명]/step_result.json"
  exit 2
fi
```

> 이 가드는 **3분 + Sheets API 토큰 절감**이 목적. 핸드오프의 스냅샷 경로가 stale일 가능성은 tc-팀-v2의 step6 가드로 차단됨.

tc-리뷰.md의 **2차 리뷰 (품질 + 수정본 구조 회귀)** 규칙에 따라 진행:

- **1차 수정 반영 확인**: 이전 리뷰 파일과 1:1 대조 (반영/미반영/부분반영 명시)
- **EVAL-03**: 재현 스탭 품질 (모호한 표현, 누락 조건, 기대결과 불명확)

- **EVAL-09**: 1TC 1검증 원칙 위반
- **EVAL-11**: 취소선/추후구현 항목 TC 포함 여부 (confluence_raw.md 기반)
- **EVAL-13**: 결정 테이블 조합 커버리지

**⚠ 필수: 수정1에서 신규 추가된 TC 범위에 대한 구조 회귀 검사**
1차 수정 결과(`step6_result.json`의 `added_count`)와 1차 리뷰 보고서(`review_[탭명].md`의 신규 TC 처방)에서 추가 TC ID 범위 식별.

- **EVAL-05 회귀**: TC ID 연속성 (수정으로 삽입된 행의 ID가 기존과 충돌/중복 없는지)
- **EVAL-06 회귀**: 분류 그룹핑 (수정 TC가 올바른 소분류 위치에 삽입되었는지)

**2026-04-17 발생 사고 참조**: 수정1에서 신규 TC 21개 삽입 시 F열↔G열이 뒤바뀐 채 적재되었으나 2차 리뷰가 품질만 봐서 놓쳤음. 위 회귀 검사로 차단.

이슈 목록 작성 → `review_[탭명]_v2.md` 저장.

### 1.5단계: 조기 종료 분기 (필수)

1단계 리뷰 결과 **`total_issues == 0`** 이면 2단계를 건너뛰고 즉시 종료한다.

```
조건: critical=0 AND high=0 AND medium=0 AND low=0
조치:
  1. progress.log 에 "STEP 6 | early-exit (이슈 0건) | 수정 단계 skip" append
  2. step_result.json 저장 (fixed_count=0, added_count=0, deleted_count=0)
  3. 2단계 코드 작성·실행 금지 (불필요한 셀 쓰기 차단)
```

> ⚠️ LOW 이슈가 있더라도 2단계는 진행한다. **모든 카운트가 0일 때만** skip.
> ⚠️ "혹시 몰라 손대는" 동작 금지 — 1단계에서 이슈 없다고 판정했으면 신뢰하고 종료.

### 2단계: 수정 코드 직접 작성 → 실행

**TC를 다시 읽지 않는다.** 1단계에서 파악한 이슈를 기반으로 직접 Node.js 수정 코드를 작성하여 실행한다.

```bash
UTIL="{WORK_ROOT}/scripts/util"
SPECS="{WORK_ROOT}/team/specs"

# 1. 리뷰 보고서의 처방(처방:)을 CRITICAL → HIGH → MEDIUM → LOW 순으로 읽는다
# 2. 각 처방을 셀 주소 기준 Node.js 수정 코드로 변환하여 직접 작성
# 3. 서식 규칙(tc-생성.md) 준수 확인 후 실행
```

> ⚠️ 작성한 코드는 실행 전 **자가 검수 필수**: 셀 주소 정확성, 이슈와 수정 내용 일치, 서식 규칙 부합.
> ⚠️ Confluence MCP 재호출 금지. 취소선 검출은 `confluence_raw.md` 파일에서 수행.

tc-수정.md의 수정 규칙에 따라 CRITICAL → HIGH → MEDIUM → LOW 순 처리.
수정 완료 후 tc-생성.md 기준 서식 적용.

#### 🔍 post-write 검증 (필수 — 자기 수정/신규 분 컬럼 무결성)

> STEP 6 tc-fixer-v2와 **동일한 사후 검증**이다. 1단계의 EVAL-04/05/06 회귀는 *수정1에서 추가된 TC 범위*만 검사하므로, STEP 6이 2단계에서 직접 수정·삽입한 행의 컬럼 꼬임(F열↔G열 뒤바뀜, 2026-04-17 사고 계열)은 이 검증으로 별도 차단한다.

셀 batch update를 실행한 **직후** 아래 2종을 반드시 수행한다:

**① validate_tc_rows.js (pre/post)**:
```js
const { validatePreWrite, validatePostWrite, formatViolations } =
  require('{WORK_ROOT}/scripts/util/validate_tc_rows.js');

// 신규 행이 있을 때만 (셀 단위 수정은 pre 생략 가능)
if (newRows.length > 0) {
  const pre = validatePreWrite(newRows, { startRow: insertStartRow });
  if (!pre.ok) { console.error(formatViolations(pre.violations)); process.exit(1); }
}
// 적재 직후 (신규/수정 무관 — 항상 실행)
const post = await validatePostWrite(sheets, SHEET_ID, TAB_NAME, affectedStartRow, affectedRows);
if (!post.ok) { console.error(formatViolations(post.violations)); process.exit(2); }
```

**② S3 range read-back** — 수정·삽입한 행 범위의 G열만 재읽기해 컬럼 꼬임 확인 (tc-fixer-v2와 동일 코드):
```bash
NODE="{NODE_PATH}"
UTIL="{WORK_ROOT}/scripts/util"
# START_ROW~END_ROW = 이번 2단계에서 수정/삽입한 최소~최대 행
BAD=$("$NODE" "$UTIL/read_gsheet_data.js" "$SHEET_ID" "$TAB_NAME" --range "G${START_ROW}:G${END_ROW}" 2>/dev/null \
  | node -e "
    const r=JSON.parse(require('fs').readFileSync(0));
    const ok=new Set(['PC','모바일','PC/모바일']);
    const bad=r.rows.map((row,i)=>({row:${START_ROW}+i, val:row[0]||''})).filter(x=>!ok.has(x.val));
    console.log(JSON.stringify(bad));
  ")

if [ "$BAD" != "[]" ]; then
  echo "[CRITICAL] 컬럼 꼬임 감지: $BAD" >&2
  echo '{"status":"fail","error":"column_corruption","bad_rows":'"$BAD"'}' > "$SPECS/[기능명]/step_result.json"
  exit 2
fi
# BAD == "[]" → G열 정상 (PC/모바일 계열만)
```

- 컬럼 꼬임 감지 시 rollback: **신규 삽입 행**은 deleteRows로 삭제, **기존 수정 행은 삭제 금지**(원본 손실 방지) → fail 반환 + 수동 복구 안내. 위 코드가 step_result.json(fail) 기록 후 exit 2.
- ①② 모두 통과한 뒤에만 step_result.json(success)을 저장한다.
