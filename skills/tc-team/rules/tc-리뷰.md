## ⚡ 출력 토큰 가이드 (필수 — 모든 차수 공통)

리뷰 보고서는 **간결성 우선**. 중복·장황한 서술 금지.

| 항목 | 길이 제한 |
|---|---|
| 이슈 제목 | ≤80자 |
| 이슈 본문 | ≤120자 한 줄 |
| 처방 | ≤200자 한 줄 |
| 종합 평가 | ≤5줄 |

**금지 패턴**:
- 처방을 여러 줄로 분리 (한 줄로 통합)
- 동일 사유 반복 (대표 1건만 기재 + "동일 패턴 N건" 표기)
- 일반론적 코멘트 ("개선이 필요합니다" 등)

→ 보고서 평균 30~45% 축소 효과. fixer 입력 토큰 동일 비율 절감.

## TC 데이터 읽기

> ⚠ **v2 파이프라인(tc-팀-v2) 우선 규칙**: 핸드오프에 **시트 스냅샷 경로**가 있으면 Read 도구로 스냅샷을 직접 읽는다 (MCP·read_gsheet_data 재호출 금지). 기획서 원문도 `confluence_raw.md`/`analysis.md`를 Read로 사용 — v2 리뷰 에이전트(tc-리뷰1수정1-v2·tc-리뷰2수정2-v2, 롤백 보존 qa-reviewer-v2 포함)는 Sheets/Confluence MCP 도구가 없다. **아래 시트 직접 읽기 절차는 스냅샷 없는 단독/v1 실행 시의 폴백**이다.

TC 데이터는 스냅샷(우선) 또는 **`read_gsheet_data.js`(폴백)로 읽고, 기획서(tc_design.md)를 반드시 병행 참조**한다.

```
1. sheet_info.txt에서 SHEET_ID, TAB_NAME 확인
2. read_gsheet_data.js 로 시트 직접 읽기 (google-sheets MCP 는 제거됨):
   node "{PROJECT_ROOT}/scripts/util/read_gsheet_data.js" $SHEET_ID "$TAB_NAME" --range A:J --minify
3. specs 폴더의 tc_design.md를 읽어 기획서 구조 파악:
   - 경로: {PROJECT_ROOT}/team/specs/[기능명]/tc_design.md
   - 대/중/소분류 목록, 암묵적 요구사항, 리스크 레벨, 커버리지 매핑표 확인
4. TC와 기획서를 병행 비교하며 리뷰 진행
   - "기획서의 이 항목이 TC에서 실제로 테스트되고 있는가?" 관점 유지
   - 커버리지 매핑표의 키워드를 TC 재현스탭에서 검색하여 커버 여부 확인
5. **EVAL-10 기획서 원문 접근** (섹션 전수 대조용):
   - sheet_info.txt에서 CONFLUENCE_URL 확인
   - `mcp__mcp-atlassian__confluence_get_page`(현재 활성, 비활성 시 fallback `mcp__claude_ai_Atlassian__getConfluencePage`)로 기획서 원문의 섹션 목차 직접 추출
   - tc_design.md가 아닌 **기획서 원문 기준**으로 TC 대분류와 1:1 매핑하여 누락 섹션 검출
   - Confluence URL 없으면 specs 폴더의 analysis.md를 원문 대용으로 사용
6. **EVAL-11 취소선/추후구현 접근** (교차 검증용):
   - `mcp__mcp-atlassian__confluence_get_page`(현재 활성, 비활성 시 fallback `mcp__claude_ai_Atlassian__getConfluencePage`)로 기획서 원문 읽기 (원문 포맷 ADF/storage 유지)
   - ADF에서 `"type":"strike"` mark가 있는 텍스트 노드를 모두 추출
   - "추후구현", "추후 적용", "미구현", "TBD", "추후 개발" 등 보류 표현을 본문에서 검색
```

## 기계 EVAL 사전 패스 (precheck) — Phase1

팀장이 리뷰 CLI 호출 직전 `scripts/util/review_precheck.js`를 실행해 결과 JSON 경로를 핸드오프에 넣는다.
(룰 SSoT는 `validate_tc_rows.js` — precheck는 같은 룰 모듈을 require로 공유, 별도 룰 정의 없음)

**리뷰어 규칙 (1차·2차 공통)**:
1. 핸드오프에 `precheck_round[N].json` 경로가 있으면 **기계 판정 EVAL은 그 결과를 채택** — 해당 EVAL의 행별 재열거·재검사 **금지** (v6 실증: 동일 패턴 3건 중 1건만 잡는 LLM 비일관을 결정적 판정으로 대체한 것 — 재열거는 비일관의 재도입)
2. LLM 담당 = ① JSON의 `llm_only_evals` 목록(판단형 EVAL) ② `llmFlags`/`status:"LLM"` 항목(기계가 검출만 하고 판정을 넘긴 행) ③ `regression.mode:"llm_fallback"` 시 회귀 검사
3. precheck `violations`는 보고서 이슈로 **그대로 인용**하고 처방만 작성 (재검증 금지)
4. 핸드오프에 precheck 경로가 없거나 파일이 없으면 — 종전대로 LLM 전수 판정 (폴백, 비차단)

기계/LLM 분담: 1차 ⚙ = EVAL-02·04·05·06·08·16기계부·19①~③ / 2차 ⚙ = EVAL-14·15추출·17·18(a) + 04/05/06 회귀 — 전체 매핑표: `~/.claude/tc-team-v2/docs/stability.md` 부록 3

## 기본기능 섹션 리뷰 제외

대분류가 **"기본기능"**인 TC 행은 **EVAL-16·17(기본기능 행 전용 검사)을 제외한 모든 EVAL 검토 대상에서 제외**한다.

- **EVAL-16·17을 제외한 모든 EVAL**에서 기본기능 행은 무시 (커버리지 01·10, 케이스 02·09, 구조 04~08, 재현품질 03·07·11·13, 비고/태그 14·15·18, 분류계층 19 — 일반 품질 EVAL 전부)
- TC 수 집계, 검증단계 비율 계산(부정+예외 49~60% 등)에서도 **제외** — EVAL-02 분모에서 기본기능 TC를 뺀 뒤 비율 산출
- 기본기능 행의 TC ID 채번은 전체 통합이므로, TC ID 연속성(EVAL-05) 검증 시 기본기능 행의 ID 갭은 허용

> 기본기능 섹션은 기획팀 확인용이며, QA 리뷰 품질 기준과는 별도로 관리된다.

## 차수별 리뷰 역할 (역할 분리)

각 차수는 **명확히 분리된 역할**을 가진다. 자기 차수의 담당 EVAL만 검토하고, 담당 외 EVAL은 보지 않는다.
이전 리뷰 파일이 있으면 반드시 먼저 읽고 수정 반영 여부를 확인한 뒤 추가 검토.

### 1차 리뷰 — 구조 리뷰 ("빠진 게 없는가?")

**담당 EVAL: 01, 02, 04, 05, 06, 08, 10, 12, 16, 19** (+ EVAL-03 사전 상태 예외 6종 검출)

커버리지와 구조적 정합성에 집중한다. 재현 스탭 품질(03)의 일반 검사·중복(07)·1TC 규칙(09)은 2차 담당이라 **보지 않는다**. 단 EVAL-03 중 **사전 상태 예외 6종**(기본기능·GlobalDefine·상태 전이·시간 수량 임계값·복합 사전 상태·fixture 후보 ≥2)의 정상 TC 사전 상태 누락만 1차에서 검출한다 (기준표 판정방법 참조).

- **EVAL-01**: 기획서(tc_design.md) 대비 TC 커버리지 전수 확인 (대분류/중분류/소분류 빠짐없이)
- **EVAL-02 (기본기능 제외)**: 각 소분류에 정상+부정+예외 최소 1개씩 존재하는지 확인. **추가로 tc_design.md의 [검증단계 사전 배분표]와 실제 TC 분포를 대조** — 배분표 최소 수량 미달 소분류가 있으면 **HIGH** 이슈. **리스크 기반 비율 확인 (기본기능 TC 제외한 분모로 산출)**: `[HIGH]` 소분류 부정+예외 < 60% → **HIGH**, `[MEDIUM]` < 49% → **MEDIUM**, `[LOW]` < 30% → **LOW** 이슈. **면제 인정 (2026-07-28 단일화)**: 배분표 비고에 `[근거부족—기획질의]` 표기가 있는 소분류 행은 최소치·비율 미달을 이슈로 잡지 않는다 — 대신 해당 부족분이 tc_design.md "기획 확인 필요 항목"에 질의로 승격되어 있는지만 확인 (미승격 시 MEDIUM). 단 토큰 뒤 `(질의 불요)` 표기 행은 승격 확인도 면제 — 구조적 사유 (예: 전투 평타 회피 부정 불성립). 이 형식 밖의 자유 서술 면제는 무효 (⚠SSoT: tc-설계 §면제 형식)
- **EVAL-04**: 플랫폼 값(G열)이 PC / 모바일 / PC/모바일 외 값 없는지 확인
- **EVAL-05**: TC ID가 001부터 순서대로, 중복·빠짐 없는지 확인
- **EVAL-06**: 동일 소분류 TC가 연속 배치되어 있는지 (분산 금지). **추가로 tc_design.md의 [분류 그룹핑 트리] 순서와 실제 시트 배치 순서를 대조** — 트리 순서 위반 시 **CRITICAL** 이슈
- **EVAL-08**: 동일 대/중/소분류 최상단 1회만 표기, 이후 빈칸인지 확인
- **EVAL-10**: 기획서 원문(Confluence/analysis.md)의 **모든 섹션 제목**을 나열하고, TC 대분류와 1:1 매핑하여 누락 섹션 0건인지 확인. 누락 발견 시 **CRITICAL** 이슈. 추가로 tc_design.md의 **[기능 간 관계]** 테이블이 있으면, 교차 TC 필요("O") 항목이 TC에 반영되었는지 확인 (미반영 시 **HIGH**)
- **EVAL-12**: 상태 전이 TC 커버리지 — tc_design.md의 **[상태 전이 테이블]**이 있는 소분류를 대상으로, 모든 전이 엣지(화살표)에 TC가 존재하는지 확인. 비정상 전이(동일 상태에서 동일 이벤트 재발생) TC 누락 시 **HIGH** 이슈. 상태 전이 테이블이 tc_design.md에 없으면 상태 있는 소분류(쿨타임, 버프, 잠금 등) 직접 식별 후 전이 커버 여부 확인
- 누락 케이스 목록화 및 추가 권고

### 2차 리뷰 — 품질 리뷰 ("내용이 올바른가?")

**담당 EVAL: 03, 07, 09, 11, 13, 14, 15, 17, 18, 20** (+ 04/05/06 수정본 회귀)

TC 내용의 품질과 정확성에 집중한다. 구조(01, 02 등)는 **보지 않는다** (1차 수정 검증만 수행).

- **1차 수정 반영 확인**: 1차 리뷰 이슈 목록과 1:1 대조하여 수정 반영 여부 명시 (반영/미반영/부분반영)
- **EVAL-03**: 재현 스탭 품질 — F열 추상 표현 금지어 grep: `정상 동작` / `정상적으로` / `올바르게` / `자연스럽게` / `원활히` / `깔끔하게` / `이상 없이` / `문제 없이` / `적절히` / `적당히`. 구체적 기대 결과(화면 변화, 수치 변화, 상태 변화) 포함 여부 확인. **함수적 종속성**: [전제조건]+[행동]이 [기대결과]를 유일하게 결정하는지 확인 — "~할 수도 있다", "~에 따라 다르다" 등 비결정적 기대결과는 조건을 분리하여 별도 TC로 작성해야 함. **"또는" 패턴은 EVAL-15에서 별도 검출**
- **EVAL-07**: 중복 TC 검출 — 완전 중복 / PC+모바일 분리 / 검증단계만 다른 중복(**정상 케이스를 기대결과 변화 없이 부정·예외로 복제한 무의미 TC 포함 — 2026-06-29 학습**). **논리 부정문 복제(7차 회고, 2026-07-28)**: 정상 문장의 반대말 재서술("1,000골드인지"↔"1,000골드가 아닌지")로 만든 부정·예외 TC는 같은 관측 1회의 중복 — 검출 대상. 검출 범위는 **시트 전체(대분류 경계 무관)** — 실측: 실중복 쌍은 대부분 교차 대분류/소분류에 존재.
> ⚠ **기계 배선 (2026-07-28 신설 — 그 전까지 "검출=기계"는 문서상 주장일 뿐 tc-team 체인에 구현이 없었다)**: `tc-team/lib/dup_gate.js`가 S4 직전에 실행되어 `$WORK/dup_report.json`을 만든다. `exact`(F열 완전 동일, 정규화 후)는 **기계 확정 중복**이라 렌즈·판정자가 드롭할 수 없고, S5에서도 잔존 시 체인이 정지한다. `similar`(토큰 자카드 ≥0.85)는 정당한 분리(BVA 상·하한, 소형/대형 등)일 수 있어 **후보 리포트**이며 판정은 이 EVAL-07이 한다. 스코프는 QA 본문끼리 + 기본기능 내부끼리(기본기능↔QA 교차는 설계상 의도된 재기술이라 제외). ⚠ **중복을 인지했으면 문구를 서로 비슷하게 맞추는 edit 금지** — 병합하거나 조건 차이를 F열에 드러낸다(실측: 판정자가 중복을 알고도 사전상태를 맞춰 자카드 0.94로 악화시킨 사례). **PC/모바일 분리쌍은 검출=기계(precheck round 2 V-07d — 동일 문장 분리는 HIGH 확정, 유사 분리는 llmFlags로 위임) / 분리 정당성(조작 차이 실재 여부) 판정=LLM** (v8 사고: 90쌍 일괄 분리를 LLM 단독 판정이 놓침 → 기계화)
- **EVAL-09**: tc-생성.md 규칙 준수 여부:
  - 1 TC = 1 검증 포인트 위반 ("A되고 B되는지" 형태) — **1NF 위반**: 하나의 TC에서 독립된 2개 이상의 검증을 수행하면 분리 권고
  - 재현 스탭에 플랫폼 중복 기재 ("PC에서", "모바일에서"로 시작)
  - 부정+예외 합계 < 49% (배분표 비고 `[근거부족—기획질의]` 면제 행은 판정 제외)
  - 경계값 TC에 구체적 수치 미명시

## TC 품질 EVAL 기준

> ⭐ **이 표가 EVAL 정의·판정 방법·담당 차수의 단일 소스(SSoT)다.** 위 "차수별 리뷰 역할" 섹션은 각 EVAL의 검출 방법·처방 상세를, 아래 보고서 양식은 기록 형식을 제공한다. **EVAL의 정의/심각도/담당 차수를 변경할 때는 이 표를 먼저 고치고 다른 섹션을 맞춘다** (드리프트 차단).

리뷰 시 아래 20개 Eval 항목을 **자기 차수 담당 항목에 한해** 명시적으로 PASS/FAIL 판정하고 보고서에 기록한다.

### 처방 작성 규칙 (필수)

**tc-fixer는 판단 없이 처방만 실행하는 코더다.** 리뷰어는 이슈마다 fixer가 그대로 실행할 수 있는 처방을 반드시 작성해야 한다.

#### 처방 형식

```
처방: [실행 유형] [대상] [내용]
```

| 실행 유형 | 처방 예시 |
|----------|----------|
| 재현스탭 수정 | `처방: TC-012 F열 수정 — '[현재 재현스탭 전문]' → '[새 재현스탭 1줄 초안]'` |
| 검증단계 변경 | `처방: TC-034 E열 수정 — '부정' → '예외'` |
| 플랫폼 변경 | `처방: TC-056 G열 수정 — 'PC' → 'PC/모바일'` |
| 신규 TC 추가 | `처방: [소분류명] 소분류에 신규 TC 추가 — 검증단계: 예외, 플랫폼: PC/모바일, 재현스탭 초안: '[1줄 초안]'` |
| TC 삭제 | `처방: TC-078 삭제 — 취소선 항목 기반` |
| 비고 추가 | `처방: TC-090 J열 추가 — '추후 구현'` |

> 재현스탭 초안은 완성된 문장이 아니어도 된다. Haiku가 초안을 받아 `[사전조건]+[행동]+[기대결과]` 형식으로 완성한다.
> 처방 없이 `권고: ~하세요` 식으로만 작성하면 fixer가 처리할 수 없다. 반드시 처방 형식을 지킨다.
> **신규 TC 추가 처방**은 tc-수정.md "신규 TC 처방 포맷"의 **7필드**(검증단계 / 플랫폼 / 재현스탭초안 / 옵션1-A / 비고 / 삽입위치 / 근거)를 모두 채운다.

## 완료 보고 형식

**출력 스타일 (보고서 본문)**: 간결한 평문 한국어로 작성한다. caveman-ko 등 토큰 압축 스타일은 적용하지 않는다 — `review_*.md`는 fixer와 사람이 함께 읽고 fixer가 `처방:`을 파싱하므로 가독성·파싱 안정성을 우선한다. 위 "출력 토큰 가이드"의 길이 제한을 지켜 중복·장황한 서술만 피한다.
- `처방:` 필드는 fixer가 Haiku로 재현스탭을 완성하므로, 초안이라도 의미가 온전한 완성 문장으로 쓴다 (너무 짧으면 실패).
- TC ID, 파일명, 심각도 라벨(CRITICAL/HIGH/MEDIUM/LOW), 처방 6필드명은 원형 그대로 유지.
- 예시: "EVAL-01 FAIL. 소분류 '길드 해체' TC 누락. design 5.3 배분표 있음, 시트 미반영."

## 학습 패턴 축적 (리뷰 완료 후 필수)

리뷰 보고서 작성 완료 후, 발견한 이슈가 **기존 규칙 파일(tc-생성.md, tc-수정.md, tc-설계.md)에 이미 예방 규칙이 있는데도 재발한 것인지**, 아니면 **새로운 유형의 반복 이슈인지** 판별한다.

### 판별 절차

1. `tc-학습-이력.md`의 "적용완료" + `tc-학습.md`(활성) 패턴에서 이번 이슈와 동일 패턴이 있는지 확인
2. **동일 패턴 재발**: 규칙이 있는데도 재발 → tc-학습.md(활성)의 해당 패턴에 `재발 N회` 카운터 추가 (이력에만 있던 패턴이면 활성으로 `재발감시` 복귀). 규칙 파일의 해당 항목 강화 검토 필요 표기
3. **신규 발견**: 1회 발견 → tc-학습-관찰.md에 1행 append (승격 대기). 같은 유형 2회+ 재발 → tc-학습.md(활성)에 신규 P-번호로 등록

### 신규 패턴 등록 형식

```markdown
### P-XX: [패턴명] `미적용`

- **빈도**: 높음/중간/낮음 (발견 건수: N건, 발견 기능: [기능명1, 기능명2])
- **발생 단계**: tc-writer / tc-fixer / tc-설계
- **증상**: [구체적 증상]
- **원인**: [추정 원인]
- **권고 예방 규칙**: → [어떤 규칙 파일]에 [어떤 내용] 추가 권고
- **적용 대상**: [규칙 파일명] ([어떤 섹션])
```

> **1회만 발견된 이슈는 패턴으로 등록하지 않는다.** 다음 리뷰에서 같은 유형이 재발하면 그때 등록한다.
