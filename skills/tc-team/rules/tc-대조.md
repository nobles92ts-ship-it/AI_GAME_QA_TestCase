# § 1. 실행 가이드 (HOW)

## 1.0 가용성 게이트 (배포 안전 — CRITICAL)
- **tc-대조는 필수 단계가 아니라 선택 플러그인이다.** 파이프라인은 대조 없이도 유효한 TC를 낸다(현행 동작).
- 이 파이프라인은 GitHub로 공개·공유된다. **기본 가정 = 받는 사람은 '뇌'가 없다.** 그 환경에선 대조 + 기획서 탐색·질의까지 **통째로 건너뛴다.**
- **모드는 `off` / `on` 둘뿐** (auto·런타임 프로브 없음):
  - **`off` (배포 기본값)**: 대조 통째 스킵. `dxr_crossref.json` 미생성. 분석→설계 직행(현행 동일). **기획서 탐색·뇌 질의 일체 안 함.**
  - **`on` (브레인 보유자 로컬 설정)**: 대조 실행. **단 fail-safe** — 별도 프로브 없이 그냥 뇌에 질의를 시도하고, 어떤 런에서 안 닿으면(context-mode 미탑재·색인 없음·에러) **로그만 남기고 스킵(파이프라인 중단 금지)**. 평소엔 항상 실행, 사고 나도 TC는 계속.
- **1회 셋업** (설치 시 config 없을 때만 — 매 런 묻지 않음):
  - 질문: *"기획서를 분석·연결·색인해둔 '뇌'가 있나요?"* (뇌가 뭔지 = 셋업 가이드 참조)
  - **없다 → `off`** (영구 스킵).
  - **있다 → `on`** → 셋업이 그 뇌(색인 `source` / manifest 경로)를 **찾아 보여주고 사용자가 확인** → 확정값을 머신-로컬 config에 저장.
  - config 있으면 다시 묻지 않는다.
- **경로는 대조 config에 두지 않는다**: 실제 기획서 경로는 각자의 **뇌 manifest(roots)** 가 보유. 대조 config = **모드(off/on) + 색인 source 이름**만.
- **머신-로컬·미커밋**: config는 공개 레포에 커밋 금지(gitignore). 레포엔 **기본값 `off` + 셋업 가이드**만 동봉. 가이드는 *"뇌가 뭔지 + off/on 설명"*만 — **뇌 만드는 법은 적지 않는다**(목적 외).
- **배포 위생**: 공개 레포엔 **이 스킬(규칙)만** 올리고 **뇌 코퍼스(DXR 원문)는 올리지 않는다.** 데이터 없이도 스킬은 무해(게이트가 자동 비활성).

## 1.1 역할
- **입력 ⚠ (2026-09-09 확장 — 오너 지시 "기획 확인 요청은 DXR을 먼저 검색해 정말 모르는 영역인지 확인하고 올려라")**: **`tc_design.md`의 "기획 확인 필요 항목" 블록 전량**(= 대조 시점에 사람에게 물으려고 줄 세워 둔 것 전부)을 입력으로 삼는다. 여기에 `analysis.md`의 **C-1 미지정 목록** + **B-2 외부 의존성 표**를 합집합으로 더한다(analysis.md를 직접 파싱 — candidates.json엔 C-1/B-2가 직렬화되지 않으니 입력원으로 쓰지 말 것). 같은 항목이 양쪽에 있으면 **중복 카운트 금지**.
  - ⛔ **"기획 확인 필요 항목 = C-1 승급본"이라는 옛 전제는 폐기.** 실측상 그 블록에는 C-1(`N (미지정)`·`TBD`) 말고도 **C-2 분석자 코멘트(모호·불명확 지점)**, **상호작용 명세 부재**(tc-분석.md §배치·좌표 서술 가드 5항 — "근거 없으면 케이스 생성 대신 승격"), **레퍼런스 TO-BE 미응답**이 함께 올라온다. C-1만 대조하면 **나머지가 뇌에 한 번도 안 물어본 채 사람에게 간다** — 이 확장이 막으려는 구멍이 정확히 그것이다.
  - 입력 항목마다 `dxr_crossref.json`에 **1건씩 반드시 결과를 남긴다**(무적중이어도 `keep`). 결과가 없는 항목 = 미대조이며, 미대조를 "알 수 없는 영역"이라고 부르지 않는다.
- **처리**: 각 항목을 뇌(`ctx_search`, `source`=config.crossref_source 기본 `"brain-corpus"`)에 대조 → §1.3 4분기 결정트리.
- **출력**: `dxr_crossref.json` (설계가 소비 — 배선은 후속, §3 참조).
- ⚠ **분석/설계 컨텍스트를 늘리지 않기 위해 자체 호출(별도 컨텍스트)로 돈다.** 입력은 위 목록만, 규칙은 이 파일만, 결과는 작은 JSON으로만 넘긴다. (STEP1 비대화 → 누락 방지)

## 1.1-a 실행 시점 — 본 대조 1회 + 델타 대조 2회 (2026-09-09 오너 지시)

> **"최근에 생기는 것들은 dxr 검색 부터."** 본 대조는 S1→S2 사이 한 번뿐이라 **그 시점의 목록만** 본다.
> 「기획 확인 필요」는 그 뒤에도 태어난다(S4 적대 리뷰의 신규 지적). 그것들은 이미 끝난 `dxr_crossref.json`에
> 존재할 수 없으므로 **뇌에 한 번도 안 물어본 채 사람에게 질의로 나갔다.** 델타 대조가 그 구멍을 막는다.

| 시점 | 모드 | 입력 | 왜 거기인가 |
|---|---|---|---|
| S1→S2 (본 대조) | — | 기획 확인 필요 항목 전량 ∪ C-1 ∪ B-2 | 설계 검수·수정이 답을 쓸 수 있는 가장 이른 지점 |
| **S4→S5 (델타)** | `fixplan` | `fix_plan.json`이 **새로 다는** 「기획 확인 필요」(리뷰어 사유를 질의문으로, F열을 문맥으로) | S5 적용 **전**이라 뇌가 찾아낸 답이 TC 기대값까지 채울 수 있는 유일한 시점 |
| **S7 FINAL-5a→5b (델타)** | `final` | 5a가 방금 쓴 `_labels.json`의 「기획확인」 배열 ∪ 최종 TC 비고열=「기획 확인 필요」 행 | **사람에게 나가기 직전 마지막 그물** — 출처가 어디든 100% 걸린다. 패널 문장이 태어난 직후라 **그 문장 자체가 질의 키**가 되어, 답을 찾은 질문을 패널에서 빼는 완전일치가 성립한다 |

- **배선(결정론·비차단)**: `crossref_delta()` 함수(정의 `tc-team/scripts/crossref_delta.sh` 한 곳)가 두 지점에서 호출된다 — S4는 `run_pipeline_full.sh`, S7은 `finalize.sh` FINAL-5a 검증 직후.
  수집 `lib/crossref_delta_collect.js` → 대조 에이전트(`tc-team-대조`, 같은 4분기·같은 가드) → 병합 `lib/crossref_delta_merge.js`(id 기준 멱등, counts는 `crossref_counts_normalize.js`와 동일 산식으로 전량 재계산).
  - ⚠ **S7 이 5a 뒤인 이유 (2026-09-11 이관)**: 구 자리(S6→S7, finalize 앞)는 주입 대상 `_labels.json`이 태어나기 **전**이라 전 런 주입 0건이었다. 자리만 5a 뒤로 옮겨도 0건이다 — 주입기는 패널 문장 ↔ 대조 `term` **완전일치**인데, 패널 없이 모은 term 은 TC 비고열 문장이다(실측: 기능A 질의 14·주입 0 / 아이템_수집 질의 9·주입 0). 수집부터 5a 뒤라야 한다.
  - **term 은 수집기 소유**: 병합기가 `--input`(수집 입력)으로 term·tc_id·context 를 id 로 되돌린다. 에이전트가 고쳐 쓴 term 한 글자가 그 질의의 매칭을 조용히 끊는다 — 답이 있는데도 질문이 패널에 남는다(과거 델타 114건 중 1건 변형 실측).
  - **id 는 원장 최대 번호 다음부터**(`D4-`/`D7-` 접두별). 병합기가 id 로 덮어쓰므로 1부터 다시 매기면 재실행이 이전 델타의 다른 질의 결과를 지운다.
  - **`final` 은 새로 물을 게 없어도 원장 기준으로 매번 거른다** — 5a 가 `_labels.json`을 매번 새로 쓰므로, `finalize.sh --only 5` 재실행에서 거르기를 건너뛰면 이미 답을 찾은 질문이 패널에 되살아난다.
  - 판별: chain.log `[S7-델타대조] 기획확인 패널 — 답 있는 질문 R건 제거 · 남은 질문 M건 (질의 Q · 판정 J)`. Q>0 인데 판정 0이면 `[S7-델타대조][경고] 패널 질의 Q건 중 판정 0건` 이 남는다(에러 없이 0건으로 끝나는 모양을 숫자로 드러낸다). 경고 기준이 「제거 0」이 아니라 「판정 0」인 이유 — 답을 찾은 질문이 없는 런은 제거 0이 정상이다.
  - ⚠ **대조 에이전트는 프로젝트 루트에서 띄운다**(본 대조 `run_pipeline_s1only.sh` · 델타 `crossref_delta.sh` 둘 다 작업 폴더를 고정). 환경변수(`CLAUDE_PROJECT_DIR`)만 박고 다른 폴더에서 띄우면 KB 가 비어 **전량 keep** 이 된다 — 답이 있는 질문이 하나도 안 빠진다(꼬리표 시절엔 「근거 없음 (뇌 대조 완료)」 거짓 꼬리표였다). 2026-09-11 대조 실측(같은 14건, 작업 폴더만 바꿈): 고정 없음 keep 11·출처 3 · "Knowledge base is empty" / 고정 keep 4·출처 10. S7 이 finalize.sh 로 옮겨와 수동 `--only 5` 가 아무 폴더에서나 돌므로 필수다.
- **소비처 = `lib/crossref_labels_annotate.js`** (`final` 모드에서만) — **필터다 (2026-09-11 오너 지시로 꼬리표 주입 폐지).** 대조가 답을 찾은 질문(`apply`·`approved:true`)은 `_labels.json`에서 **뺀다.** 남는 질문(`locate`·`keep`·`apply`+`approved:false`·원장에 없음)은 **5a 문장 그대로** `apply_labeling.js`가 찍는 「📋 기획 확인 요청」 패널로 나간다 — `→ [DXR] …` 같은 근거·출처 꼬리표를 붙이지 않는다. (파일명은 이력상 annotate 로 남아 있다)
  > 🔁 **왜 바꿨나**: 구 동작은 `정의 있음/위치/근거 없음` 꼬리표를 붙이고 **항목은 지우지 않았다.** 오너 지시 "기획 확인 요청에 작성하는 거 좋은데 물어볼 거 없으면 질문하지 않아야 해 · [dxr] 이런 건 필요 없어 · 최대한 쉽고 직관적으로 물어봐" — 답이 있는 질문은 기획자가 읽을 이유가 없고, 꼬리표는 사람에게 필요 없는 우리 쪽 근거였다(7차 시트 `아이템_수집_시스템_개선_2차` 시범 적용 → 승인 후 파이프라인 반영).
  ⚠ **대가 — 대조가 과신하면 질문이 조용히 사라진다.** 꼬리표 시절엔 틀린 `apply` 도 질문은 보였다. 그래서 뺀 질문은 `specs/<기능>/_labels_removed.json` 에 id·출처·메모와 함께 남기고(매 실행 덮어씀 — 틀린 제거를 되짚는 유일한 기록), 1건 이상이면 **완주 보고(final_report.txt)에 검토 알림**(`🔎 기획확인 패널에서 뺀 질문 N건` + 질문 1줄차·출처 목록)으로 올린다 — 파일만 두면 아무도 안 연다. 실패 배너가 아니라 성공한 런의 검토 요청이다(`.final5_removed.txt` → `chain_helpers.js final-report`). 실측(기능A 2026-09-11): 빠진 6건 중 1건이 원문에 없는 우선순위를 단정한 판정이었다(「전부 잠겼을 때 어떤 던전이 선택되나」). → §1.2-3 「의심스러우면 전환하지 않는다」의 무게가 커졌다 — **질문의 일부만 답이 있으면 `apply` 가 아니라 `locate`** 다(`apply` 는 그 질문 전체가 답해졌을 때만).
- **중복 질의 금지**: 수집기는 이미 대조를 거친 항목(term 정규화 일치 또는 tc_id 일치)을 제외한다. ⚠ 구 런 산출물에 남은 `→ [DXR …]` 꼬리표는 **비교 전에 떼어낸다** — 안 떼면 문자열이 달라져 같은 항목을 매 런 다시 묻는다(2026-09-09 음성 대조에서 33건 전량 재수집으로 실측·수정). 2026-09-11 이후 꼬리표는 새로 붙지 않는다.
- **fail-safe 동일**: 대조 `off`·뇌 미보유·에이전트 에러·수집 0건 → 로그만 남기고 체인 계속. 델타는 **한 번도 체인을 멈추지 않는다.**

## 1.2 핵심 원칙 (CRITICAL — TC 추론 금지 원칙의 적용)
1. **브레인은 발명하지 않는다.** 위치·근거(출처 페이지)만 댄다. 뇌가 반환한 내용을 넘어 추론으로 값을 지어내지 않는다. (TC 핵심 = 기획서에 없는 내용 임의 추론 금지)
2. **로컬 데이터 테이블 값 — 출처가 특정되면 값까지 쓴다 (2026-09-10 오너 지시로 잠금 해제).**
   - 🔁 **왜 풀었나 (실측 근거)**: 구 규칙은 "로컬 PC 설치 테이블 값은 **위치만 안내**하고 값 입력은 사람 몫(②)"이었다. 그런데 DXR 기획서는 수치·열거값을 xlsx 로 밀어 놓는 구조라, **답이 엑셀에 있는 항목은 아무리 정확히 찾아내도 구조적으로 TC 에 못 들어갔다.** 실측(HUD_네비_속성_표현, 2026-09-09): `in 29 / apply 0 / locate 2 / keep 27` 로 끝났는데, 같은 항목을 나중에 xlsx 로 직접 열자 `NavAreaTypeInfo` 10행·`MapInfo` DefaultNavAreaTypeIndex 가 **전부 값까지 확정**됐다. 그 사이 TC 는 이미 쓰였고(TC 022 "자유"·023 "분쟁" = 구 표기, 112·093 "안전" = 데이터상 '없음'), **틀린 기대값 5건이 사람에게 나갔다.**
   - ✅ **①apply 로 올릴 수 있는 조건 (셋 다 충족 — AND)**:
     1. `{WORK_ROOT}\<프로젝트>_관리\_테이블맵.md` 에 **파일·시트·컬럼이 등재**되어 있다 (§1.5 테이블맵 직접 대조로 확인).
     2. 원본 셀 값을 읽었다 — **`specs/<기능>/xlsx_extract.md` 에 그 시트 블록이 있으면 충족**이다. 테이블맵의 요약이 아니라 원본을 코드가 뜬 것이다.
     3. `source` 에 추출본 **블록 제목을 그대로** 옮겼다 — `<파일>.xlsx > <시트> (<N>행, <빌드>, <날짜>)`. 빌드가 제목에 들어 있으므로 아래 「빌드를 밝힌다」도 함께 충족된다.
   - 조건 충족 시 `approved:true` 로 세운다 → 확정 스펙으로 TC 에 반영된다. 하나라도 미충족이면 종전대로 **②locate**.
   - 🔧 **원본은 대조가 열지 않는다 — 체인이 미리 떠 둔다 (2026-09-11 교체)**: STEP 2-대조 직전 `lib/xlsx_extract.js` 가 기획서가 지목한 시트를 원본에서 떠 `xlsx_extract.md` 로 내려놓는다(본 대조·S4·S7 델타 공통). 에이전트는 **Read 만** 한다.
     > 🔁 **왜 바꿨나**: 전날 이 자리에 "Bash 로 python openpyxl 을 돌려 열어라"는 레시피를 두었으나, 다음 런(기능A 2026-09-11)에서 **원본 열람 0건**이었다 — locate 21건 중 13건이 xlsx 컬럼을 지목하고 note 에 "로컬 xlsx 미열람"만 남겼다. 직접 원인은 에이전트 정의·체인 핸드오프 3곳에 남은 옛 금지 문구였지만(같은 날 삭제), "LLM 에게 코드 실행을 부탁하는 규칙"은 §1.4 스텁 가드와 같은 모양으로 무너진다. 사실은 코드가 소유한다.
     - 추출본 규칙: **시트명이 기획서에 직접 등장하고 `xlsx_extract_max_rows`(기본 200) 이하면 전량**, 그 밖(큰 시트 · `<파일>.xlsx` 만 지목된 파일의 다른 시트)은 기획서 값 토큰과 **칸이 정확히 같은 행만**. 블록에 "⚠ 부분"이 붙어 있으면 **거기 없는 행은 없다는 뜻이 아니다** → 필요한 행이 안 보이면 locate.
     - 추출본의 2행째는 한글설명(`design` 범위 = 기획 메모)이다. **데이터가 아니다** — 그 문구와 기획서가 어긋나면 값 확정이 아니라 기획 확인 대상이다(실측: `DungeonResetTime` 설명칸 "로컬 시간 기준" vs 기획서 v27 "UTC 기준").
   - ⚠ **읽은 빌드를 반드시 밝힌다.** 트렁크(`DX_Trunk`)와 마일스톤 빌드(`DX 2026 M6` 등)의 값이 다를 수 있다. TC 의 「테스트 환경」과 **같은 빌드**의 xlsx 를 읽는다. 다르면 apply 금지(→locate).
   - ⚠ **여전히 금지**: 테이블에 **없는** 값을 인접 행에서 유추하기, 컬럼 의미를 이름만 보고 단정하기. 읽은 셀 그대로만 쓴다(§1.2-1 발명 금지는 그대로 살아 있다).
3. **의심스러우면 전환하지 않는다.** 틀린 전환 1건이 헛 기획확인 10건보다 나쁘다. 확신 없으면 ④(유지).

## 1.5 뇌 질의 프로토콜
- 도구: `ctx_search(queries=[...], source=<config.crossref_source>)`. **source 는 `team/tc_config.json` 의 `crossref_source`(기본 `"brain-corpus"`) 를 읽어 사용** — 하드코딩 금지(2026-07-11 적대리뷰 #24: 각자 뇌면 자기 색인 이름). 항목들을 모아 **한 번에 배치 질의**(라운드 최소화).
- 질의어: 항목마다 **2종을 함께** 던진다.
  - ⓐ **키/용어형** — 항목의 키/용어 2~4개 (예: `"TargetRange 사거리 표기 규칙"`, `"어그로 전이 규칙"`).
  - ⓑ **내용어형 (필수)** — 그 규칙이 *무엇이 어떤 조건에서 어떻게 되는지*의 명사·동사 (예: `"세공 버튼 출력 조건 잠금 딤드"`, `"어그로 전이 사망 재타겟 우선순위"`).
  - **질의는 내용어 6개 이하로 유지** (2026-08-07 실측): `ctx_search`는 **AND** 매칭이라 단어를 하나 더 붙일 때마다 그 단어까지 같은 청크에 있어야 한다. 실제 로그 712질의 재측정 — **≤6단어 무적중 35.5% vs ≥7단어 41.6%(+6.1%p)**. 길게 쓴다고 정확해지지 않는다. 7개를 넘기려면 그 항목을 **두 질의로 쪼갠다.**
  - **범용 수식어를 붙이지 마라 — 길이보다 이게 먼저다 (2026-08-19 실측 결함)**: AND 매칭에서는 붙인 단어가 **전부** 같은 청크에 있어야 하므로, `분류`·`정의`·`목록`·`규칙`·`제한`·`종류`·`값` 같은 **범용 수식어 한 개가 질의를 통째로 죽인다.** 위 6단어 상한을 지켜도 무적중이 나는 주경로가 이것이다. 실측 대비 — `DungeonCategory Enum 던전 카테고리 분류`(5단어) **0건** vs `DungeonCategory Enum 던전 카테고리`(4단어) **적중** / `CurrencyType Enum 재화 골드 다이아` **0건** vs `CurrencyType 재화 종류 Enum` **적중** / `친구 최대 수 FriendAdd 상한 제한` **0건** vs `최대 친구 수 친구 시스템` **적중**. 규칙: **고유명사(테이블·Enum·컬럼명) + 도메인 명사 2~3개까지만.** 설명하는 말은 빼라 — 그건 사람에게 하는 말이지 색인에 있는 말이 아니다.
  - **왜 ⓑ가 없으면 안 되나 (2026-07-31 실측 결함)**: 문서 **제목으로 질의하면 제목·출처·갱신이력만 든 메타데이터 헤더 청크가 1위**로 잡힌다. 본문이 없으니 스텁으로 보이고 §1.4 스텁 가드가 발동해 `keep`으로 떨어진다 — **같은 문서를 내용어로 물으면 규칙 본문이 정상 반환되는데도.** 실측: `아이템_툴팁_-_버튼_표시_규칙`(3,462자, 값까지 완전한 규칙)이 이 경로로 `keep` 처리되어 확신도 항목 18건(14.1%)이 불필요하게 감점됐다. ⓐ만 던지면 구조적으로 재발한다.
- **계층 가드 (CRITICAL — 2026-07-11 적대리뷰 #10)**: `ctx_search` 결과 각 청크의 헤더 `### [계층/도메인] 경로` 를 반드시 확인한다. **근거로 채택(apply/locate/discover의 source)할 수 있는 것은 `[D/DXR]` 헤더 청크뿐.** `[R]`(과거 TC 산출물 specs·tc_design), `[P]`(스킬·개인메모리), `[E]`(리뷰·피드백) 청크는 **위키 정의가 아니므로 근거 금지** — 이것들만 걸리면 그 항목은 `keep`. (순환 인용: 과거 tc_design 을 위키 정의로 오인해 TC가 과거 TC를 근거로 재생산하는 것을 차단. note 에 채택 청크의 헤더 경로를 남긴다.)
- **테이블맵 직접 대조 (2026-07-11 적대리뷰 #11, FTS 의존 끊기 — 2026-09-10 `locate 전용` 딱지 제거)**: 로컬 테이블 값 후보는 FTS 랭킹에 밀려 위치를 못 찾는 경우가 많다. 판정 전 항목의 **테이블/컬럼명으로 `Grep`** 을 `{WORK_ROOT}\<프로젝트>_관리\_테이블맵.md` 에 직접 돌려(예: `Grep pattern="StatusGroup" path=_테이블맵.md`), 적중하면 note 에 **xlsx 파일·시트·컬럼·조인율**을 기재한다. 테이블맵 미존재/무적중이면 종전대로 위키 위치만 안내(②locate).
  - ✅ **적중했으면 거기서 멈추지 말고 `xlsx_extract.md` 를 본다** — 테이블맵은 색인이지 값이 아니다. 추출본에 그 시트 블록이 있으면 §1.2-2 세 조건 충족 → **①apply(`approved:true`)**, 블록이 없거나 필요한 행이 없으면 ②locate. 추출본에 없는 값으로 apply 하지 않는다. (원본을 직접 여는 것은 대조의 일이 아니다 — §1.2-2 🔧)
  - ⚠ 종전 경고는 유효하다 — **SynapseMap 요약 수치와 트렁크 스냅샷은 다를 수 있다.** 그래서 근거는 항상 **원본 xlsx 를 읽은 값**이고, note 에 **어느 빌드 경로에서 읽었는지**를 적는다.
- 1홉 한계: `ctx_search`는 매칭 페이지만 반환(자동 그래프 전개 없음). 역참조/유사 시스템이 결과에 보이면 **필요한 것만 1홉 후속 질의**.
- **능동 탐색(③)**: 마지막에 1회 — `"이 기능 유형(보스/몬스터)에 보통 적용되는 DXR 공통 규칙 중 대상 페이지에 빠진 것?"`. 결과는 **후보일 뿐, 사실 단정 금지** → 전부 ③(기획확인+후보)로만. (여기서도 계층 가드 적용 — `[D/DXR]` 근거만.)

## 1.6 무적중·빈 입력 처리 (비파괴 원칙 — CRITICAL)
- **대조는 절대 상황을 악화시키지 않는다 (monotonic).** 못 찾으면 현행과 동일, 찾으면 딱 그만큼만 이득.
- 한 항목이 뇌에서 **아무것도 안 끌리면** → **④ keep** (전환 0, TC 영향 0). 기존 기획확인 그대로 설계로.
- ⚠ **거의 다 무적중이면 결과가 아니라 신호다 — 재질의 게이트 (2026-08-19 신설 / 2026-09-10 커트라인 하향, CRITICAL)**
  - 🔁 **발동 조건: `keep / in ≥ 0.8`** (구 조건 `keep == in` 에서 하향). **왜 낮췄나 (실측)**: 구 조건은 커트라인이 100% 라 **한두 건만 걸려도 게이트가 통째로 잠들었다.** HUD_네비_속성_표현(2026-09-09) 실측 — `in 29 / keep 27 / locate 2` = **93% 전멸인데 `keep == in` 이 아니라서 재질의를 안 했다.** 그 결과 xlsx 에 답이 다 있던 항목들이 `keep` 으로 사람에게 나갔고, TC 5건이 틀린 기대값으로 굳었다. 「게이트가 안 무는 두 모양 ①0%/100% 포화 자리」의 교과서 사례다.
  - `keep/in ≥ 0.8` 이면 keep 확정 **전에 반드시 1회 재질의**한다. `in < 5` 인 소량 배치도 예외 없다(비율이 거칠어질 뿐 비용은 싸다).
  - 재질의 결과는 **counts 와 함께 로그에 남긴다** — `재질의: keep 27/29(93%) → keep 8/29(28%)` 형태. 게이트가 돌았는지 안 돌았는지가 로그만 보고 갈려야 한다(안 남기면 이번처럼 조용히 통과한 게 사후에도 안 보인다).
  - 원 규칙(전부 무적중일 때):  한 배치의 질의가 **전부** `No results found` 로 오면, 그건 "뇌에 없다"가 아니라 **"질의를 잘못 던졌다"** 일 가능성이 훨씬 크다. 이때는 keep 으로 확정하기 전에 **반드시 1회 재질의**한다 — 각 항목을 **고유명사 위주 2~3단어로 줄여서**(§1.5 범용 수식어 금지 적용) 다시 던진다. 재질의도 전멸할 때만 진짜 keep 이다. 실측(업적_타입_추가, 2026-08-19): 24질의 전멸 → 동일 색인에 짧은 질의로 재시도하니 **11질의 중 10건 적중**, 최종 판정이 `keep 25` → `locate 17 / discover 2 / keep 8` 로 뒤집혔다. 이 게이트가 없으면 **뇌를 켜 두고도 대조 이득이 0인 런이 조용히 성공으로 끝난다.**
- ⚠ **keep 확정 전 마지막 관문 — 참조 기획서(`$SPEC/linked/`) 직접 확인 (2026-09-10 신설, CRITICAL)**
  - **왜**: 본문이 가리키는 같은 사이트 위키 페이지는 M-052 선수집으로 `$SPEC/linked/<pageId>_<제목>.md` 에 **이미 내려받혀 있다.** 그런데 대조는 그 파일을 한 번도 열지 않았다 — 뇌 색인(`ctx_search`)만 뒤졌다. 그 결과 **답이 참조 기획서에 적혀 있는데도 `keep`** 으로 떨어졌고, 확신도가 그 항목을 −25~45 깎았다. 실측(2026-09-10, 스펙 29·TC 5,405건): **R3 가 전체 TC 의 57%에서 발화**하고 대조 해소율은 5%(apply 51+discover 6 / 1,093)였다 — 어느 감점보다도 큰 자리다. 코드베이스 전체의 `linked` 참조가 **0건**이었다는 것이 직접 증거.
  - **어떻게**: `keep` 으로 떨어질 항목이 하나라도 있으면, 확정 전에 `$SPEC/linked/*.md` 를 **항목의 고유명사로 `Grep`** 한다(폴더가 없으면 이 관문은 건너뛴다). 적중하면 §1.2 판정표를 그대로 적용한다 — **값까지 읽혔으면 ①apply**, **위치·정의만 확인됐으면 ②locate**. `source` 에 `linked/<파일명>` 과 적중 근거를 남긴다.
  - **로그 의무**: 관문이 돌았는지가 로그만 보고 갈려야 한다 — `linked 관문: 파일 2개 / keep 후보 27건 → apply 3 · locate 6 · keep 18` 형태. 파일이 0개면 `linked 관문: 참조 문서 없음` 으로 명시한다(침묵 금지).
  - ⛔ **경계 — 근거로만 쓰고 범위로는 쓰지 않는다.** linked 문서를 커버리지 슬라이싱 대상으로 승격하지 않는다(`SKILL.md` §참조문서 · `rules/tc-분석.md` §3.8 그대로 유효). 여기서 얻는 것은 "그 용어의 정의가 어디 있나"뿐이고 **TC 를 새로 낳지 않는다.** 기획서를 2건 이상 받은 경우는 종전대로 `confluence_raw.md` 병합이 정답이다.
  - **계층 가드와의 관계**: linked 는 본 기획서가 명시적으로 가리킨 **Confluence 원문**이므로 `[D/DXR]` 청크와 동급 근거다. 여전히 금지인 것은 `[R]`(과거 TC 산출물)·`[P]`·`[E]` 로, 이 관문이 그 문을 열지는 않는다.
- **새로 시작하는 콘텐츠**(DXR에 선례 없음)라 대조 대상이 통째로 없으면 → 전 항목 `keep`, `counts.keep == in`. 설계는 현행과 100% 동일하게 진행.
- **C-1 미지정 + B-2가 둘 다 비면** 대조 자체를 스킵(early exit)하고 빈 `dxr_crossref.json`(`counts.in=0`)만 남긴 뒤 설계로 넘긴다.
- 뇌·색인 장애(검색 불가)도 동일 처리: **전 항목 keep + 스킵 사유 로그** → 파이프라인 막지 않음.

# § 2. 출력 스펙 (WHAT)

## 2.1 dxr_crossref.json (강제 구조)
```json
{
  "source_run": "<기능명/런 식별>",
  "items": [
    {
      "id": "C1-3",
      "term": "TargetRange",
      "branch": "locate",
      "source": "사거리_표기_규칙",
      "note": "정의=시전 최대거리(m). 실제 값은 로컬 [스킬테이블] 확인 요망",
      "approved": false
    }
  ],
  "discovered": [
    {
      "rule": "자동사냥 on/off 적용 여부",
      "source": "자동사냥_시스템",
      "confidence": "low",
      "as": "기획확인+TC후보"
    }
  ],
  "counts": { "in": 12, "apply": 0, "locate": 0, "discover": 0, "keep": 0 }
}
```
- **`apply`라도 값이 외부면 `approved:false`**로 두고 사람 승인 대기(→ 기획확인 요청 기록). 위키에 값까지 완전할 때만 `approved` 후보.
- **`source` 비면 그 항목은 무효** — `keep`으로 강등(가드 §1.4).
- **`counts`로 효과 측정**: 들어간 N → 분기별 수. count_gate 식 게이트·A/B(대조 on/off) 비교의 근거.

## 2.2 자체 검증 체크리스트
```
[ ] 모든 item에 branch ∈ {apply, locate, discover, keep}
[ ] apply/locate/discover 전부 source 있음 (없으면 keep)
[ ] keep 후보가 있으면 `$SPEC/linked/*.md` Grep 1회 수행 (파일 0개면 '참조 문서 없음' 로그)
[ ] 스텁·(작성중)·(홀드)·애매 → keep (전환 0건)
[ ] 로컬 테이블 값 = locate (값을 지어내 apply한 것 0건)
[ ] counts.in == items 길이, 분기 합 == in
```

# § 3. 설계 연결 계약
> ⚠ **배선(2026-06-19 결정론화)**: 대조는 STEP2 직전 **run_pipeline.sh가 전용 `tc-대조-v2` 에이전트를 bash로 결정론 호출**해 `dxr_crossref.json` 생성(`crossref_brain=on`일 때). 검수(STEP2)·수정(STEP3)이 이 JSON을 **직접 소비**. 검수 에이전트 self-gate(LLM 자율 실행) 방식은 **폐기** — 검수원이 대조를 자율 스킵해 미발화하던 버그 픽스(v4·v5 실측). `tc-설계.md` 본문(L372/L541) 직접 편집은 미배선 → STEP3가 `dxr_crossref.json` 기반 **best-effort 적용**(analysis.md/tc_design.md 외과 수정). 아래는 소비 계약.
- `apply` (**`approved:true`만** — 위키에 값까지 완전) → 설계 **커버리지 매핑표**에 확정 규칙(+출처). STEP3(needs_fix 트리거)가 소비. **`approved:false`(값이 외부/로컬 테이블)는 확정 금지 → `locate`와 동일 처리**.
  - **신뢰 앵커 게이트 (2026-07-12 적대리뷰 #14)**: vault 는 무인 Sonnet 머지 산출물이라 오염 가능 → `apply(approved:true)` 항목은 **반드시 `page_id`(+가능하면 원본 URL)를 수록**해 추적성을 남긴다. 근거 청크에 `<!-- REVIEW: 원문 미확인 주장 -->` 마커(weekly STEP 3.5.1)가 있으면 apply 금지 → `locate` 강등(사람 확인). apply 는 실측상 극소수(전 런 통산 ~1건)라 이 게이트 비용은 무시 가능.
- `locate` / `apply(approved:false)` → 설계 **"기획 확인 필요 항목 (DXR 대조)"** 블록에 출처/위치 첨부("여기 보면 됨"). **배선(2026-07-12 적대리뷰 #9)**: 이 둘은 needs_fix 트리거가 아니므로 STEP3가 안 돌 수 있다 → run_pipeline.sh가 **STEP4 직전에 `crossref_annotate.js`(결정론·멱등)로 `dxr_crossref.json`에서 직접 tc_design.md에 주입**한다. STEP3의 LLM 소비에 의존하지 않음(locate-only 런에서도 반드시 설계·시트에 반영). "STEP4가 흡수한다"는 옛 문구는 폐기 — 흡수기가 명시적 스크립트로 존재.
- `keep`    → 전환 없음. 기존 기획확인 그대로(대조가 아무것도 추가/삭제 안 함).
- `discover`→ 설계 **커버리지 매핑표**에 TC 후보 + 기획확인. STEP3(needs_fix 트리거)가 소비.
