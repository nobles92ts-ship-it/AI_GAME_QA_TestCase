# TC 생성 운용 지침

> **목적**: tc-설계 단계에서 확정된 설계 내역(tc_design.md)을 읽어 TC 양식(10컬럼)에 맞게 스프레드시트로 코딩한다. 분석/설계 판단은 하지 않으며, 설계 결정을 그대로 옮기는 역할.

모든 답변과 보고는 **한국어**로 작성한다.

---

## ⚡ ROLE INDEX (역할별 필수 섹션)

| 역할 | 필수 로드 | 선택 |
|---|---|---|
| **writer (TC 신규 작성)** | 핵심 체크리스트 / 컬럼 구조 / TC 작성 규칙 / 기본기능 섹션 / 분류 그룹핑 / C~F열 검증 규칙 / 플랫폼 적용 / J열 화이트리스트 / 미구성(공란) 데이터 동작 TC 작성 금지 / F열 설계 태그 인용 금지 / F열 "또는" 표현 규칙 / 서식 규칙 / 작업 흐름 / 완료 전 자가 검증 / 완료 보고 형식 | 추후 구현 항목 |
| **fixer (TC 수정 — 서식 적용 시)** | 컬럼 구조 / C~F열 검증 규칙 / J열 화이트리스트 / F열 설계 태그 인용 금지 / 서식 규칙 | 분류 그룹핑 |
| **updater (TC 갱신)** | 컬럼 구조 / 기본기능 섹션 / 분류 그룹핑 / J열 화이트리스트 / 서식 규칙 | C~F열 검증 규칙 |
| **reviewer (간접 참조)** | C~F열 검증 규칙 / J열 화이트리스트 / F열 설계 태그 인용 금지 | — |

> **Tip**: 자기 역할 섹션만 Read offset/limit 또는 Grep으로 우선 로드하면 단계당 ~5-8K 절감.

## 핵심 체크리스트 (작성 전 반드시 확인)

| #   | 규칙                                                | 위반 예시                                                 |
| --- | --------------------------------------------------- | --------------------------------------------------------- |
| ✅   | 1 TC = 1 검증 포인트                                | "A되고 B되는지 확인" → 분리 필수                          |
| ✅   | (사전 상태)에서 (행동)하면 (구체적 기대 결과)가 되는지 확인 — 개행 없는 단일 서술문 | "W 키를 누르면 이동하는지 확인" (조건 없음) |
| ✅   | 추상적 표현 금지 ("정상 동작", "정상적으로" 등)     | "정상 동작하는지 확인" → FAIL                             |
| ✅   | 재현 스탭에 플랫폼 중복 기재 금지                   | "PC/모바일에서 ~하면" → FAIL                              |
| ✅   | 경계값 TC에 구체적 수치 필수                        | "마나가 부족할 때" → "마나 49/소모 50인 상태에서"         |
| ✅   | 부정 + 예외 합계 ≥ 49% — **하한**. 배분표(분석 후보)가 60%를 넘기면 그 값이 정답 (천장화 금지, ⚠SSoT: tc-설계 기준). 배분표 비고 `[근거부족—기획질의]` 면제 행은 미달 판정 제외 (tc-설계 §면제 형식 단일) | 49% 미만 → 엣지 부족. 비율 맞추려 후보 케이스 쳐내기 금지 |
| ✅   | 소분류별 정상 ≥ 1 (전체 정상 비율 고정 하한 없음 — 배분표 따름) | 정상 0개 소분류 발견 시 보강                              |
| ✅   | 소분류별 정상·부정·예외 최소 1개씩 (면제는 배분표 비고 `[근거부족—기획질의]` 단일 형식만 유효) | 예외 케이스 유형 표 참조                                  |
| ✅   | 동일 분류 연속 배치 (흩어짐 금지)                   | groupByCategory 함수로 처리                               |
| ✅   | 분류 중복 표기 금지 (최상단 1회만)                  | renumberAndDedup 함수로 처리                              |
| ✅   | 추후 구현 기능도 TC 작성 (비고=추후 구현, 결과=N/A) | 기획서 기재 항목은 반드시 포함                            |
| ✅   | Output Format 템플릿 잔류 금지                      | `Output Format: '[사전 상태]에서...'` → 완성 문장 필수    |
| ✅   | 수식 대신 직접값 입력                               | INDIRECT() 등 수식 → #ERROR! 원인. JSON 기반이므로 불필요 |
| ✅   | 추가 케이스는 기존 그룹 내 삽입                     | 시트 끝에 append → 분류 분산 CRITICAL 유발               |
| ✅   | HIGH 리스크 소분류 부정+예외 ≥ 60% (`[근거부족—기획질의]` 면제 행 제외 — 36행과 동일) | 58.3% → EVAL-02 FAIL                                     |
| ✅   | 미구성(공란) 데이터 동작 TC 작성 금지 — 대상 행 셀 공란이면 스킵, 실제 값 보유 대상으로 교체 | 컬럼 일반 설명만 보고 공란 행 동작을 TC화 (issue #4) |

## 컬럼 구조 (10컬럼, 순서 엄수)

| 열  | 컬럼명      | 값 규칙                                                 |
| --- | ----------- | ------------------------------------------------------- |
| A   | TC ID       | `=TEXT(ROW()-1,"000")` 수식 — 행 삽입/삭제 시 자동 갱신 |
| B   | 대분류      | 같은 분류면 최상단 1회만                                |
| C   | 중분류      | 같은 분류면 최상단 1회만                                |
| D   | 소분류      | 같은 분류면 최상단 1회만                                |
| E   | 검증단계    | 정상 / 부정 / 예외                                      |
| F   | 재현 스탭   | (사전 상태)에서 (행동)하면 (구체적 기대 결과)가 되는지 확인 — 개행 없는 단일 서술문, 왼쪽 정렬 |
| G   | 플랫폼      | PC / 모바일 / PC/모바일                                 |
| H   | PC 결과     | PASS / FAIL / BLOCK / 미진행 / N/A                      |
| I   | 모바일 결과 | PASS / FAIL / BLOCK / 미진행 / N/A                      |
| J   | 비고        | 왼쪽 정렬, WRAP 없음                                    |

### tc_data.json 행 형식 (writer 공통 — 순서 엄수)

모든 writer가 생성하는 JSON 배열 각 행은 **7개 문자열**:

```
["대분류", "중분류", "소분류", "검증단계", "재현스탭", "플랫폼", "비고"]
// idx 0     idx 1     idx 2    idx 3     idx 4 ⚠    idx 5 ⚠  idx 6
//   B         C         D        E         F ⚠        G ⚠      J
```

> **⚠ CRITICAL — 순서 엄수 (2026-04-17 재발 사고)**:
> 반드시 **재현스탭(index 4) → 플랫폼(index 5)** 순.
> 반대로 쓰면 시트에 F열=플랫폼, G열=재현스탭으로 뒤바뀜.
> 과거 사고: 2026-04-17 아바타_탈것_합성_확정_시스템 TC 176~196(21개)에서 컬럼 꼬임 발생. 2차 리뷰까지 놓쳐 배포됨.

> **⚠ 전 행 채움(full-fill) 계약 (Phase1·L4-02)**: B/C/D(대/중/소분류)는 **모든 행에 값**을 쓴다.
> "그룹 첫 행만 쓰고 이후 빈칸" 방식은 **시트 표시 규칙**(create_gsheet가 자동 dedup)이지
> 데이터 계약이 아님 — 빈칸 tc_data는 validateFull이 `CONTRACT` 위반(차단)으로 처리한다.

**배열 조립 점검 — 기계 백스톱 (수기 행별 전수 점검 의무 폐지)**:
- 검증단계/플랫폼 enum·F빈값·분류 동사·진입 중복·그룹 분산·**F 번호 매김/태그 분리·동일 내용 PC/모바일 분리쌍**은
  `create_gsheet_tc_from_json.js`에 내장된 `validatePreWrite`가 업로드 전에 기계 차단한다 (exit 4 — idx4↔5 스왑도 G열 enum 위반으로 검출).
- writer는 위반 시 **열 그룹 분기 (L2P3-05)**: F열 위반 = 해당 행만 재문장화 후 재실행 / 골격 열(B~E·G·J) 위반 = 직변환·설계 결함이므로 **정지**(LLM 패치 금지, blocker 경로). 행별 수기 재점검 금지 (토큰 낭비).

**BAD 예시** (컬럼 꼬임):
```json
["전투", "스킬", "대쉬", "정상", "PC", "대쉬 시 25프레임 이동", ""]
//                           ↑ index 4=PC (틀림)   ↑ index 5=서술문 (틀림)
```

**GOOD 예시**:
```json
["전투", "스킬", "대쉬", "정상", "대쉬 시 25프레임 이동", "PC", ""]
//                           ↑ index 4=서술문 ✓    ↑ index 5=PC ✓
```

## TC 작성 규칙

### 검증단계

| 값   | 기준                                          |
| ---- | --------------------------------------------- |
| 정상 | 기능이 의도대로 동작하는 핵심 경로            |
| 부정 | 잘못된 입력·조건에서 차단·거부되는 경로       |
| 예외 | 경계값, 동시 입력, 시스템 부하 등 엣지 케이스 |

**검증단계 배분 주의 (2026-06-29 학습 반영)**
- **데칼 없는 평타·논타겟(무조건 명중)**: 회피가 성립하지 않으므로 **부정(회피) 케이스를 만들지 않는다** — "소분류별 정상·부정·예외 최소 1개"의 예외(전투 프로필 한정). 배분표 비고에는 `[근거부족—기획질의] 평타 무조건 명중 — 회피 부정 불성립(질의 불요)` 형식으로 기재 (면제 형식 단일화, tc-설계 §면제 형식).
- **무의미한 부정·예외 복제 금지**: 정상 케이스를 **기대결과 변화 없이** 부정·예외로 복제한 TC는 무의미 중복이다 — 검증단계 분리는 기대결과가 실제로 달라질 때만.
- **논리 부정문 복제 금지 (7차 회고, 2026-07-28)**: 정상 문장의 **논리적 부정문** 재서술("가격이 1,000골드인지" → "1,000골드가 아닌지" → "999골드가 아닌지")은 같은 관측 1회를 반복하는 가짜 TC — 부정·예외는 **다른 입력·조건·상태**에서 출발해야 한다 (tc-설계 케이스 도출 원칙과 동기).

### 재현 스탭 형식

- **단위**: 개행 없는 단일 문자열. 사전 상태·행동·기대 결과를 하나의 서술문 안에 인라인으로 통합한다.
- **문장 구조 (검증단계별 — 옵션 1-A)**:
  - **정상**: `(행동)하면 (구체적 기대 결과)가 되는지 확인` — 사전 상태가 분류 계층(대/중/소)에서 자명하면 **생략 가능**
  - **부정·예외**: `(사전 상태)에서 (행동)하면 (구체적 기대 결과)가 되는지 확인` — 사전 상태 **명시 필수** (타이밍·이상 상태·시작 상태가 검증 의미 그 자체)
- **사전 상태 생략 판단 기준 (정상 한정)**: 분류 계층(대=카테고리, 중=뎁스, 소=현재 화면)에서 시작 상태가 추론 가능할 때만 생략. 분류와 사전 상태가 어긋나면(예: 소분류=A 화면인데 사전 상태=B 화면) 명시.
- **"자명" 조작적 정의 체크리스트** (정상 TC 사전 상태 생략 가능 판정 — **3항 모두 충족 시 생략**, 1개라도 미충족 시 명시):
  1. **소분류 텍스트가 사전 상태의 화면/위치를 직접 표현**하는가? (예: 소분류="합성 재료 등록 화면" → 사전 상태 "합성 재료 등록 화면 진입 시" 자명)
  2. **사전 상태에 GlobalDefine 키나 임계값(60분/10건 등)이 포함되지 않는가**? (포함 시 옵션 1-A 미적용 예외)
  3. **분류 계층에서 fixture 후보가 1개로 결정되는가**? (한 카테고리에 진입 fixture가 1개만 매핑되는 경우 — 후보 ≥2면 옵션 1-A 미적용 예외)
- **옵션 1-A 미적용 예외** (정상이라도 사전 상태 **명시 필수**) ⚠ [CRITICAL]:
  1. **기본기능 섹션 (대분류="기본기능")**: GlobalDefine 키 + 기획 안내 문구 인용 + 진입 컨텍스트가 EVAL-16 검증 핵심이므로 옵션 1-A 미적용
  2. **GlobalDefine 키가 사전 상태에 포함된 정상 TC**: 키 보존을 위해 사전 상태 그대로 명시 (V-15·자동화 fixture 식별)
  3. **상태 전이 정상 TC**: 시작 상태 자체가 검증 핵심 (예: "그로기 ON 상태에서…"). EVAL-12 의미 보존
  4. **시간·수량 임계값 정상 TC**: "60분 이상 누적", "10건 도달" 같은 임계값이 검증 대상 — 분류로 추론 불가
  5. **복합 사전 상태 (부분만 자명)**: 분류 계층에서 일부만 자명한 경우(예: 화면=A 자명 + 토글=B는 분류 외) → **자명한 부분만 생략, 자명하지 않은 부분만 명시**
  6. **fixture 후보 ≥2 카테고리**: 한 대분류 카테고리 내 진입 fixture 후보가 2개 이상(예: `from_avatar_tab` / `from_quest_reward`)인 경우 — 정상 TC라도 사전 상태로 진입 경로 명시 (자동화 fixture 오선택 방지)
- **구체적 결과 필수**: "정상 동작", "올바르게" 등 추상 표현 절대 금지
- **플랫폼 미중복**: G열에 이미 표기 → 재현 스탭에 "PC에서", "모바일에서" 시작 금지
- **1 TC = 1 검증 포인트**: "A되고 B되는지" → TC 분리
- **번호 매김 금지 ⚠ (기계 차단 — v8 사고: 201행 전부 번호 형식)**: `1. ~ 2. ~` 다단계 번호·대괄호 태그 분리 전부 금지 — 사전 상태·행동·기대 결과를 조사로 잇는 **한 문장**. validatePreWrite가 HIGH로 차단(시트 진입 불가)

```
BAD:  "아이템이 인벤토리에 추가되고 보상 UI가 표시되는지 확인"
GOOD: TC-1 "아이템이 인벤토리에 추가되는지 확인"
      TC-2 "보상 UI가 표시되는지 확인"

BAD:  "스킬을 사용하면 정상 동작하는지 확인"
GOOD: "마나 50인 상태에서 소모량 50의 스킬을 사용하면 쿨타임 3초 UI가 표시되는지 확인"

### `추후 구현`이 `기획 확인 필요`보다 우선한다 ⚠ [CRITICAL · 2026-08-07]

기능이 아직 구현되지 않았고 **차차 개발할 예정**이면, 기대값(노출 여부·표시 방식 등)이 기획서에
없더라도 `기획 확인 필요`가 **아니라** `추후 구현` + H/I `N/A` 로 쓴다.

- **왜**: 구현 예정 항목은 "지금 보일 수도, 안 보일 수도 있는" 상태가 **정상**이다. 기대값을 물어도
  답은 "구현되면 정해진다" 뿐이라 질의만 소모되고, 테스터는 검증할 빌드가 없어 막힌다.
- **판별**: 기획서 설명이 `추후 구현` · `구현 예정` · `구현 요청` · `<일감>에서 추가` · `~ 확인 후 구현`
  계열이면 구현 예정이다.
- ⛔ **`삭제` 계열은 해당 없음**: "사용하지 않기로 하여 삭제"는 구현 예정이 아니라 **노출되면 안 되는 것**
  이라 지금 검증 가능하다 → 빈값 또는 `기획 확인 필요` 유지.
- **표기·명칭 질문은 별개로 남긴다**: 구현 예정 스탯의 명칭 불일치 같은 **문서 결함**은 J열이
  `추후 구현`이 되어도 기획 확인 요청(L/M열)에 그대로 둔다. J열은 "지금 검증 가능한가",
  패널은 "문서에 구멍이 있는가" — 서로 다른 질문이다.
- 근거: 2026-08-07 기능B_v2 — `기획 확인 필요` 104건 중 **74건이 구현 예정 항목**이었다
  (군중제어·디버프 48 · PVE 신규 20 · HP/MP 자연회복 2 · 탈것 스킬 레벨 2 등). QA 리드 지시로 전량 전환.

  F: "노출 조건이 '레벨 도달'일 때, 조건을 충족하면 표시되고 미충족 시 표시되지
      않는지 확인 (VisibleConditionType=LevelReached)"
```

**처리 규칙**:
1. 식별자(영문 테이블명·Enum·변수)가 **괄호 밖 주어/술어**면 → 사람 언어로 풀어 쓰기
2. 풀어 쓴 뒤 **구분·추적이 필요하면** 괄호 병기 `(식별자)` — 없어도 동작이 자명하면 생략
3. Enum 값 나열(`0~6 각각`)은 한 TC에 뭉치지 말고 **타입별/대표값으로 분리** (1 TC = 1 검증 포인트)
4. 풀어쓸 근거가 기획서에 없으면 임의 추론 금지 → **J="기획 확인 필요" + H/I=`미진행`**
5. **미지정 키(`N=미지정`)도 동일** — 값이 없어도 **사람 언어 주어 + 키 괄호 병기**(예: `고등급 강조 조건(Sample_HighGradeCondition, 미지정) 값 이상 등급…`). ⚠ 미지정 키를 문장 첫 주어로 raw 노출 금지(`Sample_HighGradeCondition(N=미지정) 등급 이상…` 식 금지 — 소환권 v6 025 사례). 미지정 키는 값이 없어 키로만 표현되다 주어화되기 가장 쉬운 회색지대

> 키 병기 자체가 금지가 아니다. GOOD `친구 50명(Friend_Relationship_MaxCount) 상태에서 추가 시 차단`처럼 **사람 언어가 주어, 식별자는 괄호 보조**면 정상. 금지 대상은 식별자가 문장을 끌고 가는 화이트박스 서술.

> **예외 (허용)**: 토스트·UI 텍스트 키 + 큰따옴표 문구 인용(`Sample_TOAST_X "보유한 소환권이 없습니다."`, `Tooltip_BTN_SampleInfo "확률 정보"`)은 문구로 QA가 이해 가능하고 자동화 메시지 추적용이라 **허용**(기본기능 문구 인용 규칙과 동일). 금지 대상은 데이터 테이블·Enum·확률/수치 로직 변수(`RewardGroup`·`GroupProb`·`Sample_HighGradeCondition` 등)가 큰따옴표 문구 없이 주어/술어가 되는 경우.

## F열 "또는" 표현 규칙 (사전조건·결과 분기 금지) ⚠ [CRITICAL]

**한 TC = 사전조건 1 + 과정 1 + 기대결과 1**. "또는" 분기 = 1NF 위반.

**금지 패턴 3종**:
- ❌ **결과 분기**: "로딩 화면 **또는** 오류 안내가 표시" / "전체 롤백 **또는** 전체 적용"
- ❌ **사전조건 분기**: "합성 실패 **또는** 성공-고급 이하 결과물 클릭" / "미획득 **또는** 1개 획득 아바타"
- ❌ **과정 분기**: "Tab 선택 **또는** 재료 등록 시"

**처리 규칙**:
1. 기획서로 결정 가능 → **두 TC로 분리** (TC-A, TC-B)
2. 기획서 판단 불가 → J="기획 확인 필요" + H/I=`미진행`

**허용 (분기 아님)**: "확정 완료 **또는** 확정 대기 중 하나로만 존재" — 결과 1개("정합성 유지") + 허용 상태 나열 (단, 허용 상태 명세가 기획서에 확정된 경우만). 그 외 모든 "또는" → 의심 → 분리/확인 필요.
