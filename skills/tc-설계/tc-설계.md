## 분류 구조 설계 기준 ⚠ [CRITICAL — 자동화 사전조건 계층]

분류는 **단순 기능 그룹핑이 아니라, 자동화 테스트의 사전조건 계층**이다.
각 분류는 재현스탭 실행 직전까지의 **셋업 단계**를 표현한다.

### 계층 정의

| 분류 | 역할 | 자동화 의미 | 예시 |
|---|---|---|---|
| **대분류** | 카테고리 / 이전 화면 / 최상위 사전 셋팅 값 | 테스트 진입 전 **최상위 컨텍스트** (빌드/모드/계정 카테고리) — fixture로 1회 셋업 | `타이틀` / `인게임` / `로비` / `친구 시스템` |
| **중분류** | 카테고리 / 뎁스 / 중간 사전 셋팅 값 | **상태 셋업 단계** — 셋업 작업 1회 실행 후 같은 중분류 TC 묶음 재사용 | `신규 계정` (계정 초기화 필요) / `인게임-UI` (인게임 진입 후 UI 오픈) / `합성 Tab 진입` |
| **소분류** | **현재 화면** (재현스탭 실행 직전 도달 화면) | 화면 진입 헬퍼 1개 — 이 화면에서 가능한 액션만 재현스탭에 기재 | `합성 재료 등록 화면` / `친구 검색 결과 화면` / `수집 항목 세부정보 화면` |
| **재현스탭** | 소분류 화면 안에서 수행 가능한 액션 + 검증 | 액션 + assert | "재료를 클릭하면 ~가 표시되는지 확인" |

### 중분류 셋업 의미 (예시)

- 중분류 = `신규 계정` → "신규 계정으로 셋업해야 한다"는 뜻 (계정 생성 fixture)
- 중분류 = `인게임-UI` → "인게임 화면 진입 → UI 오픈"까지 셋업 완료된 상태
- 중분류 = `합성 Tab 진입` → "HUD → 아바타/탈것 → 합성 Tab" 까지 도달 셋업 완료

### 자동화 코드 매핑 구조

```
[대분류 fixture] → [중분류 셋업/네비게이션] → [소분류 화면 도달] → [재현스탭 실행 + 검증]
   class scope        function scope             before each              test body
```

- **같은 대분류** TC들 → 동일 fixture 재사용 (재로그인 불필요)
- **같은 중분류**까지 도달한 TC들 → 셋업 1회 후 여러 TC 실행
- **소분류 단위**로 화면 진입 헬퍼 1개씩 작성
- **재현스탭** = 그 화면 위에서의 input + assert 만

### 분류 작성 규칙

1. **대분류는 진입 컨텍스트**로 명명 (기능명 X, 화면/모드/카테고리 O)
   - ❌ `이동 조작` → ✅ `인게임 - 이동` (이전 화면 = 인게임 진입 완료 상태)
   - ❌ `합성` → ✅ `아바타/탈것 합성` (카테고리)
2. **중분류는 도달 뎁스 + 셋업값**으로 명명
   - ❌ `점프` → ✅ `점프 (인게임 진입 후)` 또는 `인게임-점프 가능 상태`
   - 사전 셋업이 다르면 (예: 신규 계정 vs 기존 계정) 중분류 분리
3. **소분류는 현재 화면명**으로 명명
   - ❌ `이동 중 점프 거리` (동작 표현) → ✅ `이동 중 화면` (화면 표현)
   - 같은 화면에서 검증 가능한 케이스는 한 소분류에 묶음
4. **재현스탭에 화면 진입 동작 중복 금지**
   - 소분류가 이미 "합성 재료 등록 화면"이면 → "HUD에서 합성 진입 후" 같은 진입 동작 F열에 다시 쓰지 않음
   - F열은 그 화면 도달 이후의 액션만

### BAD vs GOOD (자동화 관점)

```
❌ BAD — 기능 그룹핑 관점:
  대분류: 합성
  중분류: 재료 등록
  소분류: 재료 등록 클릭
  F: "HUD에서 아바타/탈것 버튼을 클릭하고 합성 Tab을 클릭하고 재료를 클릭하면 ~"
     → 진입 동작이 F열에 다 들어감. 자동화 시 같은 진입을 매 TC마다 중복 실행.

✅ GOOD — 자동화 사전조건 계층:
  대분류: 아바타/탈것 합성       ← 카테고리 (fixture: 합성 모듈 진입)
  중분류: 합성 Tab 진입          ← 셋업 (HUD → 합성 Tab까지 1회)
  소분류: 재료 등록 화면         ← 현재 화면
  F: "재료 등록 화면에서 재료 슬롯을 클릭하면 보유 재료 목록이 표시되는지 확인"
     → 진입은 셋업이 처리. F열은 화면 위 액션만.
```

### 자가 검증 (설계 완료 전)

- [ ] 대분류 = 진입 컨텍스트 / 카테고리 표현인가? (기능 동사 X)
- [ ] 중분류 = 셋업이 동일한 TC들이 묶여 있는가? (셋업 다르면 분리)
- [ ] 소분류 = 화면명 표현인가? (동작 표현 X)
- [ ] 같은 소분류 TC들의 재현스탭이 모두 **그 화면에서 즉시 실행 가능**한가?
- [ ] 재현스탭에 진입 동작(HUD 클릭 → Tab 클릭 → ...)이 중복 기재되어 있지 않은가?

## 커버리지 완성도 원칙 (필수)

**우선순위: 커버리지(기능 영역 누락 여부) → 구조/서식**

기획서에 존재하는 기능 영역이 분류 그룹핑 트리에 없으면 반드시 추가. 아래는 **설계 단계 자주 누락되는 영역** — 반드시 확인:

| # | 기능 유형 | 확인 포인트 | 예시 |
|---|-----------|------------|------|
| 1 | **검색 기능** | 검색어 입력, 결과 표시, 결과 없음, 초기화 | 친구 검색, 아이템 검색 |
| 2 | **예외처리 전용 섹션** | 서버 이전, 계정 정보 변경, 실시간 갱신 실패 | 친구 목록 예외처리 |
| 3 | **알림/뱃지 상세 동작** | 레드닷 발생/소멸, 숫자 뱃지, 읽음 처리 | 친구 요청 레드닷 |
| 4 | **다른 기능에서의 진입점** | 채팅→친구추가, 프로필→팔로우 등 연동 | 채팅에서 친구 추가 |
| 5 | **연결 이동 기능** | 해당 기능에서 다른 콘텐츠로 이동 | 친구의 채널로 이동 |
| 6 | **추천/자동화 알고리즘** | 추천 기준, 최대 노출, 갱신 주기 | 추천 친구 알고리즘 |
| 7 | **UI 안내/팁 요소** | 툴팁, 안내 팝업, 빈 상태 가이드 문구 | 친구 UI 팁 |
| 8 | **추후 구현 항목** | 기획서 명시 추후 구현 (비고=추후 구현, 결과=N/A) | 레드닷 추후 구현 |
| 9 | **목록 내 탭/필터** | 탭 전환, 필터 조건, 탭별 빈 상태 | 길드원 탭, 추천 탭 |
| 10 | **플랫폼 전용 조작** | 모바일 전용 터치, PC 전용 키보드/마우스 | 단축키, 스와이프 |

> **설계 완료 전 자가 검증**: 위 체크리스트에서 기획서에 존재하는 항목이 분류 그룹핑 트리에 모두 포함되어 있는지 확인.
> 누락 항목 발견 시 → 분류 트리 보완 후 검증단계 배분표 재조정.

>
> ⚠ **직렬화 제외**: 본 축은 candidates.json `lenses[]`(L1~L8 닫힌 enum)에 넣지 않는다 — 설계 트리 케이스로만 전개 (candidate_schema.js S-82 보호).
> ⚠ **결정성(EVAL-03)**: 행동형 케이스는 확률 표현("우선 선택하는지") 금지, **배제·관측형**("근거리 스킬이 아닌 원거리 스킬을 시전하는지")으로 작성.

### C1. AI 패턴 선택 (스킬 표에 "사용 예시" 또는 거리 조건이 있으면)
스킬을 고립 시전하는 케이스 외에, 보스가 **언제/무엇을 고르는가**를 전개:
- **거리대별 선택**: 원거리 유지 시 근거리 스킬이 아닌 원거리 대응 스킬을, 근접 유지 시 원거리 접근 스킬이 아닌 근접/광역 스킬을 시전하는지 (배제형)
- **명시된 스킬 연계**: 기획이 명시한 2-스킬 시퀀스(예: "A 후 거리 벌어지면 B")가 동작하는지 — 기획에 적힌 연계만, 추론 금지
- **폴백/교착 방지**: 선택한 패턴의 발동 조건(사거리 등) 미충족 시 무행동 교착 없이 현재 상황에 맞는 다른 패턴으로 전환하는지
- **연속 시전 제한/풀 다양성**: 쿨타임 명시 시 쿨타임 중 재시전 차단 / 쿨타임 '없음'이면 동일 스킬 무한 반복 없이 패턴 풀이 분산되는지

### C2. 히트박스 형상·방향·치수 (범위 지오메트리가 있으면)
거리 스칼라(반지름/사거리) BVA 외에, **어떤 모양·방향으로 판정이 깔리는가**를 전개:
- **치수 SSoT 대조 [필수]**: 동일 스킬 히트박스 치수가 **본문 vs QA참조표에서 일치**하는지 대조 — 불일치 시 케이스화 + leaf 끝에 `[J:기획 확인 필요]` (보스 TC run: 돌진 `폭9m×24m` vs `사각1000×2500` 모순 사례)
- **방향성 형상 정합**: 방향성 사각/부채꼴 판정이 보스 진행·타격 방향(헤딩)을 따라 회전 정렬되는지 (측면 배치 후 관측)
- **형상 종류**: 원형 판정이 데이터 표기대로 전방위(360°)인지 부채꼴 한정인지 (후방 배치 후 피격 여부)
- **체공/이동 중 판정 타이밍**: 체공·이동형 스킬은 판정이 착지/특정 구간에만 붙는지

### C3. 데칼·범위 예고 정합 (범위 공격/데칼이 있으면 — 2026-06-18 추가)
범위 판정의 시각 예고(데칼)가 실제 판정·BT와 정합한지 전개:
- **평타·논타겟 즉발**: 데칼 없음이 정상 — 시전 시점에 범위 안이면 무조건 명중(회피·예고 불가)인지 (데칼 유무를 임의 단정하지 않음). **→ 무조건 명중이므로 평타·논타겟에는 회피(부정) 케이스를 만들지 않는다**(회피 부정은 성립 불가 — 2026-06-29 학습: 망령의_기사 "범위 없는 평타는 무조건 피격됨")
- **AoE 데칼 선행 [필수]**: 범위 공격에 데칼(예고 장판)이 선행 표시되는지 — 미표시 시 케이스화 + 기대결과에 "데칼 누락 = 조립 실수(버그)"
- **후속/연계 범위 변경**: 후속 공격에서 범위가 바뀌면 바뀐 범위로 데칼이 새로 표시되는지 — 미갱신 시 조립 실수
- **BT 기준 동일 범위 = 데칼 1회**: BT상 범위가 같은 스킬/연속 타격은 데칼이 1회만 표시되는지 — 2회 이상 재표시 = 조립 실수. 새 데칼은 BT상 범위가 실제로 바뀔 때만
- **돌진형(1회 판정 타이밍이 어색한 경우)**: 데칼은 경로 전체로 길게 1회, 실제 판정은 위치별 시간차로 분할 적용되는지

> **전개 의무**: 위 C1·C2·C3 해당 항목은 분류 그룹핑 트리 `→` 케이스 + 검증단계 배분표에 반영. 미해당 항목은 사유 없이 생략 가능(8렌즈와 달리 빈칸 격자 강제 아님 — 파일럿 범위). dedup(과적용 억제)은 본 파일럿 범위 외.

## 교차 중복 사전 검출 (설계 시 필수)

## 기본기능 검증 항목 추출 (tc_design.md — 분류 그룹핑 트리 바로 위)

**목적**: 비 QA(기획자)가 개발 완료된 스펙이 의도대로 구현되었는지 **5~25분 내** 1차 검수. 핵심 동작·문구·수치 확인용. 깊은 QA 시나리오(네트워크 끊김, 동시성, 스트레스)는 하위 대분류로 이관.

**구성 비율 (기획서 복잡도 따라 ±α 조정 가능)**:

| 유형 | 권장 개수 | 기획자 체크 포인트 |
|------|----------|------------------|
| 정상 (Happy Path) — 각 핵심 소분류당 1개 | 15개 전후 | "화면·기능이 정상 동작하는가" |
| 부정 (핵심 실패 메시지) | 7~10개 | "토스트·Dimmed가 스펙대로인가" |
| 경계값 (기획 수치 반영) | 2~4개 | "MaxCount·기간 등 수치가 맞는가" |
| 레드닷/알림 (조건부 노출·해제) | 1~2개 | "알림이 올바른 타이밍에 뜨는가" |
| **대분류 총량** | **25~30개** | **검수 소요 시간 약 25분** |

**포함 대상 (반드시 추출)**:
- 보이는 UX — 버튼 활성/비활성(Dimmed), 화면 진입·전환·표시

- 핵심 수치 — MaxCompoundCount, ReRollValidDate 등 기획서 상수값 반영 확인
- 레드닷/배지/알림 — 조건부 노출과 해제 타이밍

**제외 대상 (하위 대분류로 이관)**:
- ❌ 네트워크 끊김/재연결 시나리오 (서버 회귀 — QA 영역)

**추출 규칙**:

## 분류 그룹핑 트리 (tc_design.md — 원천 섹션들 바로 아래, 합성 단계)

**목적**: tc-writer가 TC를 시트에 **이 트리 순서대로, 명시된 케이스 목록대로 배치**하도록 강제.

**작성 규칙**:

1. 대분류 → 중분류 → 소분류 순으로 확정된 트리 구조
2. tc-writer는 이 순서를 그대로 시트에 반영 (순서 변경 금지)
3. GAP TC 추가 시에도 **해당 소분류 위치에 삽입** (끝에 append 절대 금지)
4. 트리에 없는 분류를 tc-writer가 임의로 추가 금지
5. **소분류 항목 아래 `→` 케이스를 설계에서 명시** — tc-writer는 이 케이스 목록대로만 TC 작성 (자체 케이스 추가·삭제 금지)
6. **케이스 수 = TC 수 (기본 1:1)**: tc-writer는 `→ 정상/부정/예외-N:` 케이스를 1:1로 TC로 변환 (재현스탭 문장 작성만 담당). **1:N 분할은 사유 화이트리스트 3종만 허용** (L3-1 — v7 실측 81케이스→85행): ①복합문 분리(1 TC=1 검증 포인트) ②플랫폼 분리 ③추후구현 의존 분리. 단 설계가 아래 형식 고정을 지키면 ①은 발생하지 않는다 — **leaf 1줄 = 검증 포인트 1개**

**케이스 작성 형식**:
```
- [소분류명] [리스크] [플랫폼]
  → 정상-1: [무엇을 확인하는지 한 줄 설명]
  → 정상-2: [추가 정상 시나리오 (필요시)]
  → 부정-1: [어떤 잘못된 조건·입력에서 차단되는지]
  → 예외-1: [어떤 경계값·엣지 케이스인지]
```

**형식 고정 ⚠ [CRITICAL — 기계 파싱 계약 (배분표 기계 대조·Phase3 직변환의 전제, 6표본 실측 변형 차단)]**:
- 트리 전체를 ``` 코드펜스로 감싸지 **않는다** (토스트 사례 — 파서가 계층 추출 불가)
- 대분류·중분류 계층은 위 형식의 리스트/볼드 단일형 — `### N. 제목` 헤딩 변형 금지 (스나이퍼 사례)
- 태그는 `[리스크] [플랫폼]` 대괄호형만. leaf 접미 주석도 대괄호 태그만 — `← B-9 L5` 류 화살표 주석 금지 (근거는 배분표 비고 열에)
- leaf 어미는 `~는지`로 통일 (`~는지 확인`으로 끝내지 않는다 — writer 어미 변환 시 중복 발생)
- **복합문 leaf 금지**: '~되고 ~되는지' 등 복수 검증 포인트를 한 leaf에 묶지 않는다 — 설계 단계에서 분리 (1 leaf = 1 검증 포인트)
- **J열 태그 기계가독 (L3-6)**: 추후구현·기획확인 케이스는 leaf 끝에 `[J:추후 구현]` / `[J:기획 확인 필요]` / `[J:버그ID-####]` 대괄호 태그로 명시 — 자유 서술("비고에 X 명시") 금지, **J 화이트리스트 값 그대로** (writer가 기계 유도 가능해야 함)

**수치 포함 필수 규칙** (CRITICAL):
케이스 설명(`→`)에 analysis.md A-2 스킬/기능 테이블의 **프레임·시간·거리·횟수·쿨타임·최대대상수** 수치를 반드시 포함한다. 수치가 있는데 케이스 설명에 빠지면 tc-writer가 재현스탭에서도 누락하므로 **설계 단계에서 원천 차단**.

```
# BAD — 수치 누락
→ 정상-1: 대쉬 사용 시 캐릭터가 빠르게 이동하는지

# GOOD — 수치 포함 (재현스탭에 그대로 반영됨)
→ 정상-1: 대쉬 입력 시 캐릭터가 전방으로 25프레임(0.417초) 이동 모션을 재생하는지
```

**사람 언어 서술 규칙** (CRITICAL — 소환권 데이터 식별자 노출 재발 방지):
케이스 설명(`→`)은 **QA·기획자가 바로 재현 가능한 동작·조건·결과**를 주어로 쓴다. 데이터 테이블명·Enum 타입명·내부 판정변수(예: `RewardGroup_Package`·`ClassType`·`VisibleConditionType`·`SpawnCondition`)를 **문장의 주어/술어로 쓰지 않는다** — tc-writer가 그대로 재현스탭에 전사해 QA가 못 알아본다. 사람 언어로 풀어 쓰고, **구분·추적이 필요할 때만** 괄호로 병기(`동작/상태(식별자)`). 풀어쓸 근거가 기획서에 없으면 임의 추론 금지 → C-1 미지정 처리.

```
# BAD — 데이터 식별자가 주어/술어 (writer가 그대로 전사)
→ 정상-1: RewardGroup_Package의 모든 보상이 ClassType 불일치인 패키지
→ 정상-1: VisibleConditionType 0(None)~6(LevelReached) Enum이 각각 정상 적용되어 SpawnCondition 판정이 타입별로 올바르게 처리되는지 확인

# GOOD — 사람 언어 주어 + 필요시 괄호 병기 + 타입별 분리
→ 정상-1: 받은 패키지의 보상이 전부 내 직업과 맞지 않을 때(RewardGroup_Package·ClassType 불일치) 받기/사용이 차단되는지
→ 정상-1: 노출 조건이 '레벨 도달'일 때 조건 충족 시 표시 / 미충족 시 미표시되는지 (VisibleConditionType=LevelReached)
```
> 키 병기 자체는 금지가 아니다. `친구 50명(Friend_Relationship_MaxCount) 상태에서 추가 시 차단`처럼 **사람 언어가 주어·식별자가 괄호 보조**면 정상. 금지 대상은 식별자가 문장을 끌고 가는 화이트박스 서술. Enum 값 나열(`0~6 각각`)은 한 케이스에 뭉치지 말고 타입별/대표값으로 분리(1 TC = 1 검증 포인트). **예외(허용)**: 토스트·UI 텍스트 키 + 큰따옴표 문구(`Summon_TOAST_X "문구"`)는 문구 인용이라 허용 — 금지는 데이터·확률/수치 로직 변수가 문구 없이 주어가 되는 경우.

> **자가 검증**: 분류 그룹핑 트리 완성 후, analysis.md A-2 테이블의 모든 수치 컬럼(프레임/초/거리/쿨타임/최대대상수/타격횟수)이 해당 소분류 케이스에 1회 이상 등장하는지 전수 확인. 누락 시 케이스 보완 후 배분표 재조정. **+ 식별자 주어화 0건**: 케이스 설명에 데이터 테이블명·Enum·내부 변수(영문 PascalCase/snake)가 **괄호 밖 주어/술어**로 등장하면 사람 언어로 재작성(괄호 병기는 허용).

**케이스 식별자 형식**: `→ {정상|부정|예외}-{N}: {설명}`
- `정상-N`: N번째 정상 케이스 (기대 동작 성공 경로)
- `부정-N`: N번째 부정 케이스 (잘못된 입력·조건 차단 경로)
- `예외-N`: N번째 예외 케이스 (경계값·엣지·비정상 상황)

**케이스 도출 원칙** (리스크 레벨 연동):

- 리스크가 높을수록 부정·예외 케이스를 촘촘히 도출 (아래 "리스크별 부정+예외 비율" 참조)
- 케이스 개수는 기획서의 실제 조건·상태·입력 경우의 수에 따라 결정 — 고정 수량 없음
- BVA 4포인트(min-1, min, max, max+1)가 적용되는 소분류는 해당 4개 케이스 모두 명시
- 상태 전이 엣지/결정 테이블 조건 조합이 있으면 엣지·조합마다 케이스 작성

**예시**:
```markdown
1. **친구 UI 진입 및 기본 구조** (대분류)
   1.1 UI 진입 (중분류)
       - HUD 메뉴 진입 [LOW] [PC/모바일]
         → 정상-1: HUD 친구 버튼 클릭 시 친구 창이 열리는지
         → 부정-1: 빠른 연속 클릭(500ms 내 2회) 시 창 중복 열림이 없는지
   1.2 키보드 조작 (중분류)
       - 단축키 열기 [LOW] [PC]
         → 정상-1: F 키 입력 시 친구 창이 열리는지
         → 부정-1: 인게임 컷씬 재생 중 F 키 입력 시 창이 열리지 않는지
```

> **tc-writer 의무**: 트리에 명시된 케이스 외 TC 추가 금지. 케이스 수보다 많은 TC 생성 시 리뷰 FAIL.

## GlobalDefine 키 목록 추출 (tc_design.md — 필수)

기획서에 등장하는 GlobalDefine 키를 사전 추출 → tc-writer가 재현스탭에서 빠짐없이 참조.

1. `GlobalDefine`, 변수명 패턴(`[기능명]_[동작]_[설명]`), 설정 테이블, 토스트 키(`_TOAST_`) 모두 추출
2. 각 키의 초기값·용도·연관 소분류 기록
3. **케이스 설명에도 GlobalDefine 키 명시** — tc-writer가 재현스탭에서 누락하지 않도록
4. **분석.md C-1 미지정값 반영**: 분석.md Part C-1에 등록된 모든 키를 이 표에 포함하고 `미지정` 컬럼에 `⚠` 표기. 초기값은 `N (미지정)` 그대로 보존

```markdown
## GlobalDefine 키 목록
| 키 | 초기값 | 용도 | 연관 소분류 | 미지정 |
|----|--------|------|-----------|--------|
| Friend_Relationship_MaxCount | 50 | 친구 등록 최대 수 | 등록 개수 제한 | |
| Character_DeleteLevelLimit | N (미지정) | 캐릭터 삭제 제한 레벨 | 캐릭터 삭제 조건 | ⚠ |
```

> **tc-writer 의무**: 모든 키를 해당 TC 재현스탭에서 참조. 누락 시 V-15 검증 FAIL.
> 예: `→ 부정-1: 친구 50명(Friend_Relationship_MaxCount) 상태에서 추가 시도 시 차단 메시지`
> **미지정 키 특별 규칙**: `⚠` 표기된 키는 재현스탭에서 구체 수치를 쓰지 말되 **사람 언어 주어 + 키 괄호 병기**(예: `→ 부정-1: 삭제 제한 레벨(Character_DeleteLevelLimit, 미지정) 미만 캐릭터 삭제 시 차단`). ⚠ **키를 문장 첫 주어로 raw 노출 금지** — `Character_DeleteLevelLimit 미만…` 식으로 키가 주어가 되면 식별자 주어화 위반(소환권 v6 025 `Summon_HighGradeCondition(N=미지정) 등급 이상…` 사례). 미지정값이 결정되면 GlobalDefine 테이블만 갱신하면 되도록.

## 리스크 레벨 태깅 (소분류별 필수)

### 리스크 평가 매트릭스 (영향도 × 발생가능성)

소분류별 리스크 레벨은 **영향도**와 **발생가능성** 두 축을 독립 평가한 후 교차점으로 산출 (키워드 패턴 매칭 아님).

- **영향도**: 높음(재화/데이터/인증/동기화) / 중간(상태 전이·조건부 잠금·UI 차단·연계 불일치) / 낮음(표시·조회·연출·레이아웃)
- **발생가능성**: 높음(매 세션 주요 경로·복잡 분기·2개+ 연계) / 중간(조건부 접근·단순 조건·독립 기능) / 낮음(드문 접근·읽기 전용·단순 표시)

| 영향 \ 발생 | 높음 | 중간 | 낮음 |
|-------------|------|------|------|
| **높음** | `[HIGH]` | `[HIGH]` | `[MEDIUM]` |
| **중간** | `[HIGH]` | `[MEDIUM]` | `[LOW]` |
| **낮음** | `[MEDIUM]` | `[LOW]` | `[LOW]` |

**평가 예시**: 골드 소모(높음×높음)→`[HIGH]` / 탭 전환(낮음×높음)→`[MEDIUM]` / 레이아웃(낮음×낮음)→`[LOW]`

**리스크별 TC 수량 방향**: HIGH=부정+예외 ≥60% / MEDIUM ≥49% / LOW ≥30%. ⚠ **SSoT 동기 대상**: 이 비율(60/49/30%)은 tc-설계·tc-설계검수·tc-리뷰·tc-생성 **4파일 일치 필수** — 변경 시 4곳 동시 수정.

tc_design.md의 소분류 항목 옆에 `[HIGH]` / `[MEDIUM]` / `[LOW]` 태그 표기.

## 검증단계 사전 배분표 (tc_design.md — 커버리지 매핑표 바로 위)

TC 작성 전에 소분류별 정상/부정/예외 최소 수량을 확정.

**작성 규칙**:

0. **⚠ 분류 트리 전개 의무 (배분 전 선행) — 소환권_v2 A 부류 누락 재발 방지**: 분류 그룹핑 트리의 `→` 케이스는 analysis.md **B-3(EP)·B-4(BVA)·B-8(오류패턴)·B-9(렌즈 스윕 해당 칸) 후보를 빠짐없이 전개**한 결과여야 한다.
   - **B-9 렌즈 스윕 전개**: 매트릭스의 모든 비-`–`(해당) 칸이 트리 `→` 케이스로 전개됐는지 확인. 특히 신규 축 **L3(반복/멱등)·L4(생명주기)·L1(목록·탭 개수경계)**이 누락되기 쉬움 (소환권 v4 등급탭 0/1개·독립추첨·오버레이 잔류 사례)
   - BVA 수치 경계는 **min-1 / min / max / max+1을 개별 케이스로 분리** — `≤N / >N` 식 통합 표기 금지 (경계 손실)
   - §3.2 카탈로그의 해당 기능유형 오류패턴(만석·동시 중복·롤백·세션 중단)이 부정/예외 케이스로 반영됐는지 확인
   - ⚠ **배분 수량의 천장은 트리, 트리의 바닥은 분석 후보** — 트리가 빈약하면 배분표도 빈약해진다
1. **모든 소분류**에 정상 ≥1, 부정 ≥1, 예외 ≥1 배분 (예외 불가 시 사유 명시)
   → 배분 수치는 분류 그룹핑 트리의 `→` 케이스 수와 **반드시 일치**해야 함
2. **리스크별 부정+예외 최소 비율** (소분류 단위):
   - `[HIGH]` 소분류: 부정+예외 **≥ 60%**
   - `[MEDIUM]` 소분류: 부정+예외 **≥ 49%**
   - `[LOW]` 소분류: 부정+예외 **≥ 30%**
   - ⚠ **리스크 하향 금지 (비율 회피 차단 — 소환권 v6 사례)**: 리스크 레벨은 기능 위험도(데이터·재화 변경 / 상태 전이 / 분기 / 동시성 / 신뢰 파괴)로 **먼저 독립 확정**한다. 비율 미달은 **케이스 추가로만 해결** — 리스크를 낮춰 비율 기준을 면제받는 것을 금지(공격적 보강이 기본, 방어적 하향이 예외). **하향 허용 = 과대평가 정정뿐**: 배분표 행 비고에 `[하향 M→L | 근거: 단순성 4조건(①상태전이 ②데이터·재화 변경 ③입력→결과 분기 ④외부 의존·동시성 — 모두 없음) + 기획서 §N]` 명시. 근거 없거나 "비율 충족용" 사유 = 무효 → 케이스 추가.
3. 전체 합계 기준 **부정+예외 49~60%는 하한(바닥)** — 분석에서 도출된 BVA·오류 후보가 더 많으면 **후보 수가 우선**하며 60%를 넘겨도 무방. (⚠ 비율을 목표치로 삼아 케이스를 쳐내지 말 것 — 천장화 금지)
4. 합계 행에 비율 미리 계산
5. **분류명 3계층 완전 동일 ⚠ (기계 조인 계약, L3-3)**: 배분표의 대/중/소분류 문자열은 분류 그룹핑 트리와 **완전 동일** — 축약·개명 금지 (실측: 지상v2 '지상 이동(자동) - 네비메시 끊김 처리'를 배분표에서 '지상 이동(자동)'으로 축약 → 기계 대조 불가). validateFull/precheck가 명칭 미스매치를 위반으로 출력한다
6. **0값·미달 사유는 비고 열에 (L3-4)**: 정상 0건 또는 비율 미달이 의도된 소분류는 배분표 **비고 열에 사유를 반드시 명시** — 비고 공란인 0값/미달은 기계 검증(validateFull)이 FAIL 처리한다

```markdown
## 검증단계 사전 배분표

| 대분류 | 중분류 | 소분류 | 리스크 | 정상 | 부정 | 예외 | 소계 | 비고 |
|--------|--------|--------|--------|------|------|------|------|------|
| **합계** | | | | 52 | 40 | 50 | 142 | |
| **비율** | | | | 36.6% | 28.2% | 35.2% | 100% | 부정+예외=63.4% |
```

## 섹션 전수 대조표 (tc_design.md — 원천 섹션, 기본기능 바로 아래)

기획서의 **모든 섹션/소제목**을 1:1 나열 → 통째로 누락되는 섹션 원천 방지.

1. 최상위 ~ 2단계 깊이까지 모든 섹션 제목을 순서대로 나열
2. 각 섹션에 대응할 TC 대분류/중분류 미리 매핑
3. 매핑 안 되면 **❌ 누락 위험** 표시

**누락 고위험 패턴**:

| 패턴 | 설명 | 예시 |
|------|------|------|
| 연계 UI 표시 | 기능 A 정보가 기능 B 화면에 표시 | 강화 UI에서 수집 아이콘 |

## 커버리지 매핑표 (tc_design.md 맨 끝 — 필수)

기획서의 모든 기능/규칙/UI 요소를 1:1 나열. 설계검수(C-05·C-11~13)와 리뷰(EVAL-01/10)가 누락 판별하는 기준.

**작성 규칙**:

1. **모든** 기능, 규칙, UI 요소, 예외 처리를 빠짐없이 한 줄씩 나열 (요약 금지). **검증 최소단위(규칙·수치·표기 규칙 1개 = 1행)까지 쪼갠다** — 예: '확률 표기'를 1행으로 뭉치지 말고 `4자리 정밀도` / `5번째 반올림` / `4번째 0→1 보정` / `가변 소수점(끝 0 생략)`으로 분리. 기획서에 명시됐는데 영역 단위로 뭉쳐 누락되는 것 방지 (소환권 v4 D08 반올림보정·D09 가변소수점 사례 — 렌즈가 아닌 분해로 잡는 항목)
2. `출처` = 기획서 절/섹션 번호
3. `키워드` = TC 재현스탭에서 검색할 핵심 단어 2~4개 (구체적, 일반적 단어 금지)
4. 항목 수는 기획서 실제 내용에 따라 결정 — 단, 기획서의 모든 기능/규칙/UI가 누락 없이 포함되어야 함

```markdown
## 커버리지 매핑

| # | 기획 항목 | 출처 | 검증 포인트 | 키워드 | 리스크 |
|---|-----------|------|------------|--------|--------|
| 1 | [기능/규칙/UI] | [절] | [무엇을 확인] | [단어1,단어2] | HIGH/MEDIUM/LOW |
```

**주의**: 매핑표가 없거나 불완전하면 설계검수(STEP 2 C-05·C-12)와 리뷰(EVAL-01/10)가 누락을 판별할 수 없다 — 검수 FAIL 사유.

## 재현스탭 품질 기준 (tc_design.md 말미 — EVAL-03 대응)

tc-writer가 재현스탭 작성 시 참조할 품질 기준. HIGH 리스크 소분류는 샘플 재현스탭 1개를 tc_design.md에 제공 권장 (2차 리뷰 EVAL-03 이슈 대폭 감소).

**절대 금지 표현** (EVAL-03 즉시 FAIL): "정상 동작하는지 확인" / "올바르게 처리되는지" / "정상적으로 표시되는지" / "~할 수도 있다" / "~에 따라 다르다" — 기대 결과가 불명확하거나 비결정적인 표현.

**올바른 패턴**: `[전제조건] + [구체적 행동(수치 포함)] → [기대결과: 수치/화면상태/텍스트 변화 명시]`
- analysis.md에 프레임/시간/거리/횟수가 명시된 기능은 재현스탭에 해당 수치를 **반드시** 포함 (설계 케이스에 이미 포함되어 있어야 함)

**검증단계별 사전상태 정책 (옵션 1-A)** — tc-writer가 케이스 설명을 재현스탭으로 변환할 때 적용:
- **정상**: 사전 상태가 분류 계층(대=카테고리, 중=뎁스, 소=현재 화면)에서 자명하면 **생략 가능** → `(행동)하면 (기대결과)가 되는지 확인`
- **부정·예외**: 사전 상태(타이밍·이상 상태·시작 상태)가 검증 핵심이므로 **명시 필수** → `(사전 상태)에서 (행동)하면 (기대결과)가 되는지 확인`
- 판단 기준: 분류와 사전 상태가 어긋나면(예: 소분류=A 화면인데 사전 상태=B 화면) 정상 케이스라도 명시

**옵션 1-A 미적용 예외 (정상이라도 사전 상태 명시 필수 — 6종, tc-생성·tc-리뷰·tc-수정과 동일 세트)** ⚠ [CRITICAL]:
- **상태 전이 TC**: tc_design.md [상태 전이 테이블]에 등재된 소분류 — 시작 상태(예: "그로기 ON")가 검증 핵심이므로 정상이라도 명시. EVAL-12 검증 의미 보존.
- **시간·수량 임계값 TC**: analysis.md A-2 스킬·기능 테이블에 임계값(60분/10건/3회 등)이 명시된 케이스 — 임계값 자체가 검증 대상이라 사전 상태에 임계값 명시 필수.
- **GlobalDefine 키 사전 상태 포함**: 사전 상태에 자연스럽게 포함되는 GlobalDefine 키(예: `(Common_TOAST_X)`) — 키 보존 위해 사전 상태 그대로 유지.
- **fixture 후보 ≥2 카테고리**: 한 대분류 카테고리 내 fixture 후보가 2개 이상(예: `from_avatar_tab` / `from_quest_reward`)일 때 — 정상 TC라도 사전 상태로 진입 경로 명시. 자동화 fixture 오선택 방지.
- **기본기능 섹션 (대분류="기본기능")**: GlobalDefine 키·기획 안내 문구 인용·진입 컨텍스트가 EVAL-16 검증 핵심 — 옵션 1-A 미적용 (tc-생성 기본기능 규칙과 동일).
- **복합 사전 상태 (부분만 자명)**: 분류 계층에서 일부만 자명한 경우(예: 화면은 자명 + 토글 상태는 분류 외) — 자명한 부분만 생략, 자명하지 않은 부분만 명시.

> 위 6개 예외는 tc-writer 산출 단계에서 **분류 키워드·analysis.md·tc_design.md를 교차 참조하여 식별**. 식별되면 케이스 설명에 사전 상태를 그대로 전달.

**HIGH 리스크 샘플 형식** (권장):

| 소분류 | 검증단계 | 샘플 재현스탭 |
|--------|---------|-------------|
| [소분류명] | 부정 | 1. [선행조건] 2. [행동] 3. [기대: 구체 수치/상태] |
```
